The six scenarios (four appear on your form)

You can't choose which four you get, so study all six. Each scenario is a paragraph describing a production system, followed by a set of questions about it.

1. Customer Support Resolution Agent. A support agent built with the Claude Agent SDK handling high-ambiguity requests (returns, billing disputes, account issues) through custom MCP tools: get_customer, lookup_order, process_refund, escalate_to_human. Target is 80%+ first-contact resolution while knowing when to escalate. Primary domains: 1, 2, 5.

2. Code Generation with Claude Code. A team using Claude Code for generation, refactoring, debugging and documentation, integrating it with custom slash commands and CLAUDE.md, and deciding plan mode vs direct execution. Primary domains: 3, 5.

3. Multi-Agent Research System. A coordinator delegating to four specialized subagents — web search, document analysis, synthesis, report generation — producing comprehensive cited reports. Primary domains: 1, 2, 5.

4. Developer Productivity with Claude. An Agent SDK agent helping engineers explore unfamiliar codebases, understand legacy systems, generate boilerplate and automate repetitive tasks, using built-in tools (Read, Write, Bash, Grep, Glob) plus MCP servers. Primary domains: 2, 3, 1.

5. Claude Code for Continuous Integration. Claude Code in a CI/CD pipeline running automated code reviews, generating test cases and giving PR feedback, with a stated emphasis on actionable feedback and minimizing false positives. Primary domains: 3, 4.

6. Structured Data Extraction. Extracting information from unstructured documents, validating output with JSON schemas, maintaining high accuracy, handling edge cases gracefully, integrating downstream. Primary domains: 4, 5.

The scenarios are different settings for the same five domains. One idea, such as "enforce the rule in code rather than in the prompt", appears as a refund gate in scenario 1 and as a CI gate in scenario 5.

Three-Day Study Plan

For someone who uses Claude Code daily and needs to turn that into exam knowledge, including the API and SDK layer underneath it, which the exam tests and daily Claude Code use doesn't show you. Plan on 5–6 hours a day; if you have less, do only the starred (★) items.

The exam guide describes the exam as a test of practical judgment about architecture, configuration, and tradeoffs, not recall. Exam-day tactics

Time. 60 items in 120 minutes is two minutes each. Most take under a minute once you recognize the pattern; save the time for the four or five that are close calls.

Read the instruction line. v1.0 says multiple-choice and multiple-response. Each item states how many to select. Missing a "select two" loses the item for no reason.

Find the deciding phrase. Almost every question contains one phrase that decides the answer: must never, before any, every time, available to every developer, developers wait for, regardless of directory, the same session. Find it before reading the options.

Eliminate options by rule, not by how plausible they sound. Three rules usually work: - Remove any option that meets a must always requirement with a prompt instruction. - Remove any option that adds infrastructure (a classifier, a trained model, a routing layer, a bigger model, a bigger context window) when a description, a criterion or a schema field would do. - Remove any option that pushes work onto a human or the customer when the system should handle it.

When two options both look right, choose the one that fixes the root cause described in the question. The exam guide's explanations often reject fixes that would help but address a different problem.

Answer every item. There is no penalty for guessing, and v0.2 noted the platform requires an answer before you can move on anyway.

If you only have one day

Domain 1 — Agentic Architecture & Orchestration (27%, ~16 items)

Domain 1 is the largest domain: 27% of the exam and seven task statements. Most questions describe a production system that misbehaves and ask you to pick the fix. Two principles decide most of them:

  • When a mistake has real consequences (money, compliance, security), enforce the rule in code, not in the prompt. A prompt instruction is followed most of the time; code is followed every time.
  • Don't add machinery the failure doesn't need. If a small fix addresses the root cause, the bigger one is wrong.

In the book: Chapter 2 — The Agentic Loop (1.1) · Chapter 5 — Orchestration (1.2, 1.3) · Chapter 6 — Hooks & Gates (1.4, 1.5) · Chapter 1 — Agents & Workflows (1.6) · Chapter 7 — Sessions (1.7)

1.1 Design and implement agentic loops

An agentic loop is the code that sends a request to Claude, runs any tools Claude asks for, sends the results back, and repeats until Claude is done. Claude Code runs this loop every time you press enter; on the exam you are the one writing it.

The loop

1. POST /v1/messages  →  system, messages[], tools[]
2. Read response.stop_reason
3. If "tool_use":
     append the assistant message (with its tool_use blocks) to messages
     execute each requested tool
     append a USER message containing tool_result block(s)
     go to 1
4. If "end_turn": done — present the final response

The exam guide states three facts about it:

  • stop_reason controls the loop. "tool_use" means Claude wants a tool run, so continue. "end_turn" means Claude has finished, so stop.
  • Tool results are appended to conversation history. That history is the only place the model can see what its tools returned, so it is how the agent builds up knowledge across steps.
  • Model-driven decision-making: Claude reasons from context about which tool to call next. That is agentic design. A pre-configured decision tree or a fixed tool sequence is a different design.

The three anti-patterns

The exam guide names three wrong ways to decide the loop is finished. Expect them as distractors:

  1. Parsing natural language signals to determine loop termination: searching the response text for "done" or "I've finished."
  2. Setting arbitrary iteration caps as the primary stopping mechanism. A cap protects against a runaway loop. It does not tell you the task is complete.
  3. Checking for assistant text content as a completion indicator. A response with stop_reason: "tool_use" often contains text too, because Claude frequently says what it is about to do before calling a tool.

Answer rule. Any option that decides completion by something other than stop_reason is wrong.

Current product (not tested): current models also return "model_context_window_exceeded", meaning the response hit the context window limit mid-generation. The exam guide uses only tool_use and end_turn, and that is what is tested.

1.2 Orchestrate multi-agent systems with coordinator-subagent patterns

Hub and spoke

In a hub-and-spoke design, one coordinator agent sits in the middle and every subagent talks only to it. Subagents never talk to each other. The coordinator handles all communication, error handling and routing of information between them.

The exam guide gives three reasons for routing everything through the coordinator: observability (one place to see what happened), consistent error handling, and controlled information flow (each subagent gets exactly what the coordinator chooses to give it).

The coordinator's job:

  • break the task into pieces (decomposition)
  • hand each piece to a subagent (delegation)
  • combine the results (aggregation)
  • deciding which subagents to invoke based on query complexity, rather than running the whole pipeline every time

Subagents have isolated context. A subagent does not see the coordinator's conversation history. It knows only what the coordinator puts in its prompt. Several questions in Domains 1 and 5 depend on this fact.

Failure mode: decomposition that is too narrow

The exam guide warns that a coordinator can split a broad topic too narrowly, so the subagents between them cover only part of it. Sample question 7 shows this: every subagent succeeds, yet the report on "creative industries" misses most of the topic, because the coordinator split it into three visual-arts subtasks.

When every downstream agent worked correctly but the overall coverage is wrong, the cause is the coordinator's decomposition.

Skills tested

  • The coordinator should analyze query requirements and dynamically select subagents, instead of always running the full pipeline.
  • Partition the scope so subagents don't duplicate each other, for example by giving each one distinct subtopics or distinct source types.
  • Iterative refinement loops: the coordinator reviews the synthesis for gaps, sends targeted follow-up queries to the search and analysis subagents, runs synthesis again, and repeats until coverage is sufficient.
  • All subagent communication goes through the coordinator.

Skills tested

  • Put the complete findings from earlier agents directly into the subagent's prompt. If the synthesis subagent needs the web search results and the document analysis, the coordinator pastes both in. A prompt that says "analyze the findings" without including them is the classic wrong answer.
  • Pass context as structured data that keeps content separate from metadata (source URLs, document names, page numbers), so each claim can still be traced to its source after the handoff.
  • To run subagents in parallel, emit several Task tool calls in one coordinator response. One Task call per turn runs them one after another.
  • Give subagents goals and quality criteria, not step-by-step procedures, so they can adapt to what they find.

1.4 Multi-step workflows with enforcement and handoff

Programmatic enforcement vs prompt guidance

Programmatic enforcement means a rule is checked by code; prompt guidance means the model is asked to follow it. This is the most tested idea on the exam. In the exam guide's words: "When deterministic compliance is required (e.g., identity verification before financial operations), prompt instructions alone have a non-zero failure rate." A system prompt rule will eventually be skipped. If skipping it costs money or breaks compliance, it needs a check in code.

Prerequisite gates are that check: your code refuses to execute a tool call until an earlier step has completed. The exam guide's example is to block process_refund until get_customer has returned a verified customer ID. Sample question 1 tests the same idea; its correct option gates both lookup_order and process_refund on identity verification.

Sample question 1's explanation also says why the other options fail:

  • A stronger system prompt (B) and few-shot examples (C) both "rely on probabilistic LLM compliance, which is insufficient when errors have financial consequences."
  • A routing classifier (D) "addresses tool availability rather than tool ordering, which is not the actual problem."

Structured handoff to a human

When the agent escalates mid-task to a human who cannot see the conversation transcript, it should send a structured summary: customer ID, root cause, refund amount, recommended action. A raw transcript dump makes the human redo the agent's work.

Requests with several concerns

When a customer raises several issues in one message, split them into distinct items, investigate each in parallel using shared context, then combine the results into a unified resolution. Handling the first issue and asking the customer to open a second ticket is wrong.

1.5 Agent SDK hooks for interception and normalization

A hook is your code, registered with the Agent SDK, that runs automatically at a fixed point in the loop. The model cannot skip it. Claude Code's permission prompt is a similar idea: a check that runs before a tool executes, whatever the model intended.

The exam guide names two uses:

Purpose Hook Example from the exam guide
Change tool results before the model sees them PostToolUse (runs after the tool) Convert the mix of Unix timestamps, ISO 8601 strings and numeric status codes returned by different MCP tools into one format
Block a tool call that breaks policy Tool-call interception (runs before the tool) Block refunds over $500 and redirect to human escalation

The exam guide ties this back to 1.4: it contrasts "using hooks for deterministic guarantees versus relying on prompt instructions for probabilistic compliance." Use a hook when a business rule must always hold.

The direction matters, and it is a common distractor. PostToolUse sees results coming back from a tool. Interception sees calls going out. A PostToolUse hook cannot stop a refund, because by the time it runs the refund has already been processed.

The exam also tests the opposite mistake: don't use a hook for a soft preference. Match the strength of the enforcement to the cost of getting it wrong.

1.6 Task decomposition strategies

There are two ways to break a task into steps:

Pattern Use when Exam guide's example
Fixed sequential pipeline (prompt chaining): the same steps every time, each feeding the next The steps are known in advance Review each file on its own, then run a cross-file integration pass
Dynamic adaptive decomposition: the agent decides the next subtasks based on what it has found Open-ended investigation where you can't know the steps up front "Add comprehensive tests to a legacy codebase"

Skills tested

  • Use prompt chaining for predictable, multi-aspect reviews. Use dynamic decomposition for open-ended investigation.
  • Split a large code review into one pass per file plus a separate cross-file integration pass. The exam guide's reason is attention dilution: when one pass covers many files, the model gives each one shallower attention and can contradict itself across files. Sample question 12 (a 14-file review that comes back shallow and inconsistent) has this as its answer. Its explanation rejects two alternatives: a bigger context window "doesn't solve attention quality issues," and requiring 2 of 3 independent passes to agree "would actually suppress detection of real bugs."
  • For an open-ended task, first map the structure, then find the high-impact areas, then write a prioritized plan that changes as you discover dependencies.

2.1 Design effective tool interfaces

Descriptions drive tool selection

The model chooses which tool to call mainly by reading the tool descriptions. The exam guide: tool descriptions are the primary mechanism LLMs use for tool selection, and minimal descriptions make selection between similar tools unreliable. This is the answer to many Domain 2 questions.

A good description covers:

  • what the tool does and what it returns
  • the input formats it accepts
  • example queries
  • edge cases
  • boundary explanations: when to use this tool rather than a similar one

Failure mode: misrouting

Misrouting is the model calling the wrong one of two similar tools. It happens when descriptions are vague or overlap. The exam guide's example is analyze_content and analyze_document with near-identical descriptions.

Sample question 2 has two tools, get_customer ("Retrieves customer information") and lookup_order ("Retrieves order details"). Both descriptions are minimal and both tools accept similar identifiers, so the agent confuses them. The correct answer is expand the descriptions. The explanation rejects the other options:

  • Few-shot examples "add token overhead without fixing the underlying issue."
  • A routing layer is "over-engineered and bypasses the LLM's natural language understanding."
  • Merging the two tools is "a valid architectural choice but requires more effort than a first step warrants."

Keywords in the system prompt

Instructions in the system prompt that mention particular keywords can make the model associate those words with a tool, overriding good tool descriptions. If the descriptions are good and selection is still wrong, check the system prompt for such keywords.

Three ways to fix tool selection

Fix Exam guide's example
Rename the tool and rewrite its description so it no longer overlaps with another analyze_content → extract_web_results, with a web-specific description
Split a generic tool into purpose-specific tools, each with defined inputs and outputs analyze_document → extract_data_points, summarize_content, verify_claim_against_source
Check the system prompt for keyword-sensitive instructions —

2.2 Structured error responses for MCP tools

How a tool reports failure

An MCP tool reports failure by setting the isError flag on its result. The error comes back to the agent as readable content, not as an exception, so the agent can decide what to do next. This is why Claude Code can recover when a Bash command fails: the failure output comes back as a tool result it can read.

Current product (not tested): in the Messages API, the equivalent field on a tool_result block is spelled is_error. The exam guide only uses isError.

The four error categories

Category Meaning Retry?
transient Timeouts, service unavailable Yes
validation The input was invalid No
business The request breaks a policy No
permission Access is missing or expired No

What a good error response contains

  • errorCategory: transient, validation or permission (the categories the exam guide lists in the skills bullet)
  • isRetryable: a boolean
  • a human-readable description of what went wrong
  • for a business-rule violation, retriable: false and a customer-friendly explanation, so the agent explains the policy to the customer instead of retrying

Why a generic error is wrong

A generic "Operation failed" prevents the agent from making appropriate recovery decisions. Structured error metadata prevents wasted retry attempts on errors that will never succeed.

Two more skills

  • Subagents recover locally from transient failures. They pass to the coordinator only what they cannot fix themselves, and when they do, they include partial results and what was attempted.
  • An access failure is not the same as an empty result. A timeout is a failure that needs a retry decision. A query that ran and matched nothing is a success that returned an empty set. Options that confuse the two are a recurring distractor.

2.3 Distribute tools across agents and configure tool choice

Too many tools makes selection worse

The exam guide gives a number: an agent with 18 tools instead of 4–5 picks tools less reliably, because it has more options to choose between. Agents that hold tools outside their role also tend to misuse them; the exam guide's example is a synthesis agent that starts running web searches.

The fix is scoped tool access: each agent gets only the tools its role needs, plus limited cross-role tools for specific high-frequency needs.

Sample question 9 is the model case. The synthesis agent needs to verify facts. 85% of verifications are simple fact-checks; 15% need real investigation. The correct answer is a narrow verify_fact tool for the simple cases, with complex verifications still sent through the coordinator. The rejected options are giving synthesis full web search (too much access, and it mixes up the agents' responsibilities) and batching verifications (it makes synthesis wait on them).

The exam guide also names replacing a generic tool with a constrained one, for example replacing fetch_url with a load_document tool that only accepts valid document URLs.

tool_choice

tool_choice is a request parameter that controls whether and which tool the model must call.

Value Behavior Use for
"auto" The model decides, and may return text instead of calling a tool Normal open-ended agent turns
"any" The model must call a tool, but picks which one Guaranteeing structured output when several extraction schemas exist and the document type is unknown; making sure you don't get a conversational reply
{"type": "tool", "name": "..."} The model must call that specific tool Making one tool run first, such as forcing extract_metadata before the enrichment tools, then handling later steps in follow-up turns

Current product (not tested): a fourth value, {"type": "none"}, forces a text-only reply with no tool call. The exam guide lists only the three above.

3.3 Path-specific rules for conditional convention loading

A file in .claude/rules/ can start with YAML frontmatter containing a paths field of glob patterns:

---
paths: ["terraform/**/*"]
---

Path-scoped rules load only when editing matching files. The rest of the time it stays out of context, which saves tokens and keeps unrelated instructions away.

Path rules vs subdirectory CLAUDE.md

This distinction is what task 3.3 is about, and sample question 6 depends on it:

  • A subdirectory CLAUDE.md is directory-bound: it applies to one directory.
  • A glob rule applies to a type of file wherever it is.

Sample question 6: test files sit next to the code they test all over the codebase (Button.test.tsx beside Button.tsx), and they must all follow the same conventions, loaded automatically. The answer is a .claude/rules/ file with paths: ["**/*.test.tsx"]. The explanation rejects the others:

  • a CLAUDE.md in every directory can't cover files spread across many directories
  • one root CLAUDE.md with a section per file type relies on Claude inferring which section applies, instead of matching explicitly
  • a skill needs someone to invoke it, or Claude to decide to load it, so it isn't automatic

Rule of thumb: conventions that belong to a directory → subdirectory CLAUDE.md. Conventions that belong to a file type found in many directories → .claude/rules/ with a glob.

3.5 Iterative refinement techniques

Four techniques, each with the situation it fits:

Concrete input/output examples. When a prose description keeps being interpreted differently, show 2–3 concrete examples of input and expected output. This also fixes edge cases, e.g. test cases with example input and expected output showing how a migration script should handle null values.

Test-driven iteration. Write the tests first (expected behavior, edge cases, performance requirements), then iterate by sharing test failures with Claude each round.

The interview pattern. Before implementing, have Claude ask questions to surface things you might not have thought of. Use it in unfamiliar domains, where it brings up issues like cache invalidation strategy and failure modes.

One message or several. If the problems affect each other, describe them all in one detailed message. If they are independent, fix them one at a time.

4.1 Explicit criteria to improve precision and reduce false positives

Specific criteria beat general instructions

A false positive is a finding the model reports that isn't a real problem. The way to reduce them is to state exactly which cases count. The exam guide's example:

Instruction
Right "flag comments only when claimed behavior contradicts actual code behavior"
Wrong "check that comments are accurate"

The exam guide also says general instructions like "be conservative" or "only report high-confidence findings" do not improve precision compared with specific criteria. An option that tells the model to be more careful or conservative is wrong.

Why false positives cost so much

When one category of finding produces many false positives, developers stop trusting the other categories too, even the accurate ones.

Three skills

  • Write criteria that say which issues to report (bugs, security) and which to skip (minor style, local conventions), instead of filtering by the model's confidence.
  • Turn off a category with many false positives for a while, to win back developer trust while you improve its prompt. The exam treats this as a correct answer.
  • Define explicit severity criteria with concrete code examples for each severity level, so findings are classified consistently.

4.2 Few-shot prompting

Few-shot prompting means putting a few worked examples in the prompt, so the model copies the pattern instead of interpreting a description.

When few-shot is the answer

The exam guide calls few-shot "the most effective technique for achieving consistently formatted, actionable output when detailed instructions alone produce inconsistent results." It names four uses:

  1. Demonstrating ambiguous-case handling, such as which tool to pick for an ambiguous request, or how to report branch-level gaps in test coverage.
  2. Helping the model generalize to new patterns, not just the cases you listed.
  3. Reducing hallucination in extraction (the model inventing values), e.g. informal measurements or documents with varied layouts.
  4. Format consistency: showing the exact shape you want.

How many examples, and what they contain

Use 2–4 targeted examples for the ambiguous cases. Each example should explain why one action was chosen over a plausible alternative. An input → reasoning → output example teaches more than an input → output pair.

Other patterns the exam guide names:

  • Examples that show a specific output format; the exam guide's is location, issue, severity, suggested fix.
  • Examples distinguishing acceptable code patterns from genuine issues, which cuts false positives and still generalizes.
  • Examples that cover varied document structures: inline citations vs bibliographies, methodology sections vs details embedded in the text, narrative descriptions vs tables.
  • Examples that fix empty/null extraction of required fields by showing correct extraction from several formats.

Criteria (4.1) or examples (4.2)?

Both reduce false positives. Which one is right depends on what is missing:

  • The rule itself is undefined or vague → write explicit criteria (4.1).
  • The rule is defined, but the model applies it inconsistently, especially on ambiguous cases → add few-shot examples (4.2).

Few-shot is not always the answer. In sample question 2, the agent confuses two tools because their descriptions are thin; there, few-shot examples "add token overhead without fixing the underlying issue", and the fix is better descriptions (Domain 2).

4.3 Structured output via tool use and JSON schemas

How to get structured output

tool_use with a JSON schema is the most reliable way to get output that matches a schema. You define an extraction tool whose input_schema is the structure you want, the model "calls" it, and you read the data from the tool_use block in the response, not from its text.

tool_choice for extraction

Value Behavior Use in this domain
"auto" The model may return text instead of calling a tool —
"any" The model must call a tool, and picks which Guarantee structured output when multiple extraction schemas exist and the document type is unknown
{"type": "tool", "name": "extract_metadata"} The model must call that specific tool Ensure a particular extraction runs before enrichment steps

A schema guarantees syntax, not correctness

Strict JSON schemas via tool use eliminate syntax errors but do not prevent semantic errors, such as line items that don't add up to the total or values placed in the wrong field.

  • The JSON is malformed → the answer is a schema.
  • The JSON is well-formed but wrong → the answer is validation logic (4.4), not a stricter schema.

Schema design

Pattern Why
Optional / nullable fields for information the source document might not contain A required field pushes the model to invent a value when there isn't one. Letting it return null removes that pressure
An "unclear" enum value Gives the model an honest answer for ambiguous cases
An "other" enum value plus a detail string Lets the model record a category you didn't anticipate instead of forcing a bad fit
Formatting rules in the prompt alongside the strict schema The schema fixes the shape; the prompt tells the model how to normalize messy source formats

Current product (not tested): two newer API features strengthen the schema guarantee:

  • strict: true on a tool definition guarantees the tool's input matches the schema. Without it, forced tool_choice plus your own validation is reliable in practice but not guaranteed.
  • output_config.format: {"type": "json_schema", ...} guarantees schema-valid JSON with no tool involved; the JSON comes back in a normal text block. This suits extraction jobs like extract_invoice, where the "tool" exists only to get structured output.

Neither checks semantics. A strictly valid extraction can still have stated_total and calculated_total disagree; catching that is still the job of 4.4. There is also a fourth tool_choice value, {"type": "none"}, which forces a text-only reply; the exam guide lists only the three above.

4.4 Validation, retry, and feedback loops

Retry with the error

When an extraction fails validation, retry with the original document, the failed extraction, and the specific validation error. The error tells the model what to correct; a plain retry usually produces the same output.

When retrying won't help

The exam guide: retries are ineffective when the required information is simply absent from the source document. A retry can fix a format or structure error. It cannot produce information that was never there, for example a value that only exists in another document that wasn't provided.

So work out which kind of failure it is before retrying, and send the ones a retry can't fix to human review.

Validation the model does itself

The exam guide names two designs:

  • Extract a calculated_total next to the stated_total and flag any difference. This catches a semantic error that a schema can't.
  • Add a conflict_detected boolean for when the source data contradicts itself.

detected_pattern

Add a detected_pattern field to each finding, recording which code construct triggered it. You can then look at which patterns developers keep dismissing, which shows where your false positives come from.

4.5 Batch processing

Message Batches API facts

  • 50% cost savings compared with normal requests
  • Up to 24-hour processing window, with no guaranteed latency SLA
  • Does not support multi-turn tool calling within a single request: you can't run a tool mid-request and send its result back
  • custom_id on each request lets you match each result to its request

When to use it

Appropriate: non-blocking, latency-tolerant work nobody is waiting on: overnight reports, weekly audits, nightly test generation. Inappropriate: blocking workflows, i.e. work that blocks someone, such as a pre-merge check a developer is waiting for.

Sample question 11 is exactly this split: batch the overnight technical-debt report, keep the pre-merge check on the normal synchronous API. The explanation rejects the argument that "batches are often faster in practice" for a blocking check, and notes that results arriving out of order doesn't matter because custom_id matches them up.

Operational skills

  • Choose the API per workflow, by how long it can wait, not once for the whole organization.
  • Work out how often to submit from the deadline. The exam guide's example: batches take up to 24 hours, so to guarantee results within 30 hours, submit every 4 hours.
  • Handle failures by custom_id: resubmit only the documents that failed, with a change where needed, such as chunking documents that exceeded context limits.
  • Tune the prompt on a small sample before running a large batch, so most documents succeed first time and you avoid expensive resubmissions.

4.6 Multi-instance and multi-pass review

Why a model reviews its own work badly

A model retains reasoning context from generation, making it less likely to question its own decisions in the same session. It still has the reasoning that produced the output, so it tends to agree with it. Therefore:

Independent review instances — without the generator's prior reasoning context — are more effective at catching subtle issues than self-review instructions or extended thinking.

Extended thinking is named here as the weaker option. Don't choose it.

Several passes for large reviews

Split a large review into one pass per file plus a separate cross-file integration pass. This avoids attention dilution and contradictory findings: one pass over many files spreads attention thin and can disagree with itself across files. It is the same pattern as task 1.6, and sample question 12 (a 14-file review that comes back shallow and inconsistent) tests it.

Confidence scores: when they are valid

Task 4.6 includes this skill: "Running verification passes where the model self-reports confidence alongside each finding to enable calibrated review routing." That looks like it contradicts sample question 3, where the model's self-reported confidence is the wrong answer for deciding when to escalate. It doesn't:

  • Self-reported confidence used on its own to decide to escalate in a live conversation → wrong. It is poorly calibrated, and the agent is often confidently wrong on exactly the hard cases.
  • Self-reported confidence checked against a labeled validation set, then used to decide which items human reviewers look at first → right (see task 5.5).

Confidence is fine as an input to a calibrated routing system. It is not fine as the decision itself.

5.1 Preserve critical information across long interactions

Four risks the exam guide names

Progressive summarization risk. When a long conversation is summarized again and again (as /compact does in Claude Code), exact numbers, percentages, dates and what the customer said they expect get blurred into vague statements. Those specifics are what you most need to keep.

Lost in the middle. Models reliably process information at the beginning and end of long inputs, but may omit findings from middle sections.

Tool results pile up. Tool results consume tokens disproportionately to their relevance. The exam guide's example: an order lookup returns 40+ fields when only 5 matter.

Full history is required. The API keeps no conversation state, so every request must include the complete conversation history, or the model loses track of the conversation.

Six fixes

Fix What it means
Case facts block Copy the transaction facts (amounts, dates, order numbers, statuses) into a persistent "case facts" block included in each prompt, outside summarized history, so it is never summarized
Separate context layer When a session covers several issues, keep each issue's structured data (order IDs, amounts, statuses) in its own layer
Trim tool output at the source Drop irrelevant fields before the result enters the context, e.g. keep only the return-related fields from an order lookup
Order by position Put key findings summaries at the beginning of a combined input, and organize the details under explicit section headers
Require metadata from subagents Subagents return dates, source locations and methodology with their findings, so later synthesis is accurate
Structured facts from upstream agents When downstream agents have little context to spare, upstream agents return key facts, citations, relevance scores instead of long prose and reasoning

The common idea: keep the facts that must survive in a structured block that is never summarized, and let the rest of the conversation be compressed.

Current product (not tested): the memory tool (memory_20250818, a persistent /memories directory) and the context editing API (clear_tool_uses_20250919) are official mechanisms for the case-facts and trim-at-source problems above. They are outside this domain's tested scope.

5.2 Escalation and ambiguity resolution

Exactly three valid escalation triggers

  1. The customer asks for a human.
  2. The policy has an exception or a gap for this request. The exam guide adds: "not just complex cases." Complexity alone is not a reason.
  3. Inability to make meaningful progress.

Two invalid triggers

The exam guide calls sentiment-based escalation and self-reported confidence scores "unreliable proxies for actual case complexity." Sample question 3 (an agent that escalates easy cases and attempts hard ones) rejects both: confidence fails because "the agent is already incorrectly confident on hard cases," and sentiment "solves a different problem entirely; sentiment doesn't correlate with case complexity."

Asking for a human vs being frustrated

Two rules apply side by side:

  • If the customer explicitly asks for a human, escalate immediately, without investigating first.
  • If the customer is frustrated but hasn't asked for a human, acknowledge the frustration and offer to resolve the issue if you can. Escalate only if they then ask again.

What matters is whether they asked for a human, not how upset they are.

Policy gaps

Escalate when the policy is ambiguous or silent about the specific request. The exam guide's example: a customer asks for a price match against a competitor, but the policy only covers price adjustments on the company's own site. The policy not covering something doesn't mean it's forbidden; a human should decide.

Several matching customers

When a lookup returns multiple customer matches, the agent should ask for additional identifiers, not pick one by guessing.

Fixing an agent that escalates the wrong cases

Sample question 3's answer: write explicit escalation criteria in the system prompt, with few-shot examples of when to escalate and when to resolve. It is the proportionate first fix. A trained classifier, sentiment analysis and confidence thresholds are all wrong.

5.3 Error propagation across multi-agent systems

What a subagent's error report should contain

The type of failure · what was attempted · any partial results · possible alternative approaches. With these four, the coordinator can choose a recovery: retry with a changed query, try another approach, or carry on with the partial results.

Two anti-patterns the exam guide names

  • Silently suppressing errors: returning an empty result as if it were a success. Nothing can recover from it, and the final output may be incomplete without anyone knowing.
  • Stopping the whole workflow because one step failed.

A third, milder one: generic error statuses such as "search unavailable" hides what the coordinator needs to know. Sample question 8 (a search subagent timing out) rejects an option that retries with backoff and then returns a generic status on this basis, even though the retry part is fine.

Recover locally first

Subagents implement local recovery for transient failures, and pass up only what they can't resolve, including what was attempted and partial results.

Access failure vs valid empty result

The same distinction as in task 2.2, applied to multi-agent systems. A timeout needs a retry decision. A query that succeeded but matched nothing does not.

Coverage annotations

Mark in the synthesis output which findings are well supported and which topics have gaps because a source was unavailable. Partial results are acceptable; partial results presented as complete are not.

5.4 Context in large codebase exploration

Context degradation

The exam guide describes the symptom: in long sessions, the model starts giving inconsistent answers and refers to "typical patterns" instead of the specific classes it found earlier. If a question describes an agent that has drifted into generic advice about a codebase it explored an hour ago, this is the diagnosis.

Five techniques

Technique What it means
Scratchpad files Write key findings to a file, and refer back to it for later questions, so they survive when the context fills up or is compacted
Subagent delegation Give specific questions ("find all test files", "trace refund flow dependencies") to subagents. Their long exploration output stays in their context, and the main agent keeps the overall picture
Phase summaries At the end of one exploration phase, summarize the key findings before starting the next, and put that summary in the next phase's subagent prompts
Saved state and a manifest Each agent saves its state to a known location. After a crash, the coordinator loads a manifest on resume listing that state and puts it into the agents' prompts. This is the exam guide's crash-recovery design
/compact Shrink the context during a long exploration once it fills with discovery output

Current product (not tested): the memory tool closely matches the scratchpad and manifest patterns: a persistent /memories directory Claude reads and writes across sessions. 5.5 Human review workflows and confidence calibration

The main risk

An overall accuracy figure can hide poor accuracy on particular document types or fields. 97% overall can include 60% on one class of document. Check accuracy per document type and per field before letting high-confidence extractions skip human review.

Four techniques

  • Stratified random sampling of high-confidence extractions: keep reviewing a random sample from each segment of the extractions the model is sure about, to measure the ongoing error rate and detect novel error patterns. You sample the ones you believe are correct because that is where unnoticed errors collect.
  • Accuracy broken down by document type and field, to confirm performance holds in every segment before cutting human review.
  • Field-level confidence scores, calibrated against a labeled validation set, to decide where reviewers look. Calibrated means you have checked that, say, 90% confidence really is right about 90% of the time.
  • Send to human review any extraction with low confidence, or whose source document is ambiguous or contradictory, so limited reviewer time goes where it's needed.

Confidence is legitimate here because it is per field, calibrated against labeled data, and used to prioritize review, not to make a decision on its own (compare 5.2 and 4.6).

5.6 Provenance and uncertainty in multi-source synthesis

Provenance means being able to trace each claim in the output back to its source.

How it gets lost

Source attribution is lost during summarization steps when findings are compressed without preserving claim-source mappings. The fix is structural: require structured claim-source mappings (source URL, document name, relevant excerpt) that every later agent must preserve and merge through synthesis.

Sources that disagree

Report both values with their sources instead of picking one. If two credible sources give different figures, show both, attributed. More fully: finish the document analysis with the conflicting values included and marked as conflicting, and let the coordinator decide how to reconcile them before synthesis.

Dates

Require publication or data collection dates in structured outputs, to prevent temporal differences from being misinterpreted as contradictions. Two "conflicting" figures may just be from different years.

Current product (not tested): the citations API (citations: {"enabled": true} on a document content block) does claim-to-source mapping automatically when Claude reads a document directly, returning the cited text and its location. You still need your own mapping for handoffs between subagents, where there is no document block, only the previous subagent's findings.

Report structure

  • Separate sections distinguishing well-established findings from contested ones, keeping each source's own wording and methodological context.
  • Present each kind of content in a suitable form: financial data as tables, news as prose, technical findings as structured lists, rather than one uniform format.

Five rules that answer most questions

  1. When a mistake has real consequences, enforce the rule in code. Money, compliance, security, identity checks, required order of steps → prerequisite gate or hook. Not a system prompt instruction, not few-shot examples.
  2. Otherwise, pick the smallest fix that addresses the root cause. The exam guide's answers reject "over-engineered" options (routing classifiers, trained models, extra infrastructure) when rewriting a description or writing explicit criteria would work.
  3. Fix the root cause, not the symptom. If every downstream component works, the problem is upstream. If tool descriptions are thin, fix the descriptions rather than adding examples.
  4. Anything that must survive a handoff goes in structured fields. Sources, error details, case facts and escalation summaries should be fields, not prose the next step has to interpret.
  5. A bigger model or a bigger context window is almost never the answer.

Chapter 1 — Agents, workflows, and knowing which one you need

Most production failures with Claude are architecture failures, not model failures. A support agent refunds the wrong account because identity verification was requested in a prompt rather than enforced in code. A 14-file review contradicts itself because one call was asked to do 14 jobs. The central question is how much control flow lives in your code and how much in the model's judgement. Too little structure gives you non-determinism where you needed guarantees. Too much gives you a brittle, expensive state machine.

Domain 1 is 27% of the exam, the heaviest domain. Its questions are diagnostic: a system misbehaves in a described way, and you pick the fix. Distractors are usually sound engineering aimed at the wrong problem, or more machinery than the failure needs.

Claude Code is itself an agent built from the primitives this chapter covers: a loop, tools, a system prompt, and gates. The vocabulary comes from Anthropic's "Building effective agents" (workflow vs agent, the pattern catalogue) and the Agent SDK work (the loop).

The augmented LLM

The building block is the augmented LLM: a model plus tools, retrieval, and memory.

Underneath it is the Messages API, a single stateless call. It takes a system prompt, alternating user and assistant messages, and optional tool definitions, and returns one assistant message. It has no memory, cannot run anything, and cannot read files. Everything Claude Code does beyond that (reading the repo, editing, running tests, remembering earlier steps) is scaffolding built around this call. This book teaches you to build that scaffolding.

Each augmentation is a decision surface:

  • Tools set what the model can do, and their descriptions steer what it will do. A description is a prompt (Chapter 3). When Claude Code picks the wrong MCP tool, a description has underperformed.
  • Retrieval sets what the model knows when it acts: pre-fetched (CLAUDE.md, injected up front) or fetched on demand (the file Claude opens on turn six).
  • Memory sets what survives between turns and sessions. Subagents inherit nothing except their prompt, which is why a Claude Code subagent can't see your main thread.

Read each exam scenario by which augmentation carries the weight. The support agent's refund depends on memory of a verified customer ID. The research system's hard problem is what the coordinator carries between subagents. Extraction barely needs tools and lives or dies on schema design.

Workflows and agents

Exam options are written against Anthropic's exact definitions:

  • Workflow: LLMs and tools orchestrated through predefined code paths. You write the sequence, and the model fills in the steps.
  • Agent: the LLM dynamically directs its own process and tool usage. You give it a goal and tools, and it decides each next step from what it just learned.
  • Agentic systems: the umbrella term for both. It does not imply autonomy.

In Claude Code, a bare request is an agent: nobody told it to grep, read three files, edit, then test. A slash command whose body lists the steps in order is a workflow. Same model, same tools; only where the control flow lives differs.

The distinction is architectural, not a measure of intelligence. Task statement 1.1 tests it as model-driven decision-making versus pre-configured decision trees or fixed tool sequences. Neither is the default answer. The deciding question is whether you can enumerate the paths in advance.

The agentic loop

Anthropic's loop: gather context → take action → verify work → repeat.

  • Gather: fetch what's needed rather than being handed everything, e.g. grep/tail on a log instead of reading all of it.
  • Act: call a tool that changes something.
  • Verify: check the result against the goal.

Teams skip verification because in most domains it is expensive or impossible to automate. Nothing cheaply tells you whether a summary is good or a report has gaps. The loop decays into gather-act-gather-act, and errors compound unnoticed.

Coding became the first strong agent domain because it has free, fast, deterministic verifiers: compiler, type checker, tests. Outside coding, ask what is my test suite? It might be a JSON Schema validator (Chapter 13), or a second model call with a rubric (evaluator-optimizer, below). If no verifier exists, keep the design a workflow with human review rather than an autonomous agent.

Mechanically, the loop is a while you write. The API is stateless, so you own the message list, resending it every iteration. Each response's stop_reason says whether Claude is done or wants a tool run. Termination is a protocol signal, not a judgement call. Chapter 2 builds the loop.

The five workflow patterns

Five workflows plus the autonomous agent. For each, learn the condition that makes it right.

Pattern Shape Choose it when
Prompt chaining Fixed sequence of calls with programmatic gates between steps Subtasks are fixed and known in advance; you trade latency for per-step accuracy
Routing Classify input, send to a specialised prompt/model/toolset Inputs fall into distinct categories and misrouting is rare and recoverable
Parallelization Concurrent calls, aggregated Subtasks are independent (sectioning), or you want confidence from repeats (voting)
Orchestrator-workers A central model decomposes at runtime, delegates, synthesises Subtasks depend on what the input contains
Evaluator-optimizer Generator + critic in a loop until a bar is met Clear evaluation criteria exist and iteration measurably improves output
Autonomous agent Goal + tools + loop Step count is unpredictable, the flow can't be drawn in advance, and the environment gives actionable feedback

Details the exam turns on:

  • Chaining: the gates are what matter. Without them you have a long prompt split across calls. With them, a malformed extraction is caught at step 2 instead of step 5. Plan mode is a gate: nothing executes until the plan clears a check. The blueprint's example is per-file review passes plus a separate cross-file integration pass.
  • Parallelization has two forms. Sectioning runs independent subtasks at once, e.g. one instance answers while another screens for policy violations. Voting runs the same task several times to raise recall. Trap: requiring 2-of-3 agreement suppresses real findings rather than filtering false ones.
  • Parallelization vs orchestrator-workers: can you write the subtask list before seeing the input? If yes, it's parallelization and the split belongs in code. If no, it's orchestrator-workers and a model must decompose. When Claude Code decides for itself to spawn subagents, that is orchestrator-workers.
  • Orchestrator-workers' signature failure: every worker succeeds and the aggregate is still wrong. The defect is upstream, in the decomposition. Every subagent returns a correct answer about the wrong three files.
  • Evaluator-optimizer loops uselessly when no reliable criterion exists, because the critic can't tell good from bad.
  • Autonomous agents trade cost and latency for adaptability, so they need guardrails: sandboxing, checkpoints, human review at consequential boundaries. Claude Code's permission prompts are those guardrails. In your own agent, you build them.

Choosing

Ask in order:

  1. Can you draw the decision tree? If it's finite on a whiteboard, build the workflow. Readable code is cheaper to debug than a reasoning trace and doesn't vary between runs.
  2. Are the subtasks predictable? That is, can you enumerate them before seeing the input? This settles parallelization vs orchestrator-workers, and fixed pipeline vs dynamic decomposition.
  3. Is the task worth the tokens? An agent resends its growing history every iteration, so cost grows super-linearly with steps, and subagents multiply it. No exact multiplier is tested, only the shape: more steps and more agents cost more.
  4. What does an error cost, and would you notice? Cost and discoverability are separate axes. A wrong refund is expensive and visible. A silent coverage gap is cheap per incident and invisible. Low discoverability argues for structure and explicit verification even when errors look cheap.

Overriding rule: pick the simplest solution that works and add complexity only when it demonstrably helps. Often a single well-specified call with good examples beats any agentic design.

Chapter 2 — The agentic loop in code

Claude Code is an agentic loop — about forty lines of code — wrapped around a good tool set. The backtracking and recovery you see in it are not orchestration logic: Claude decides each next step by reasoning over the conversation history, and the loop only ferries messages and checks one field. This chapter builds that loop by hand (task statement 1.1) against the customer-support scenario: get_customer, lookup_order, process_refund, escalate_to_human.

The Messages API, from zero

One endpoint, POST /v1/messages. The request fields that matter:

Field What it is
model Model identifier.
max_tokens Ceiling on reply length.
system Persistent instructions (role, policy, tone). Separate from messages because it is not part of the conversation. This is where Claude Code sends its base prompt plus your CLAUDE.md files.
messages The conversation, oldest first. Each entry has role ("user" / "assistant") and content.
tools Tool definitions: name, natural-language description, input_schema (JSON Schema).

content can be a plain string, but its real form is a list of typed blocks:

  • text — prose.
  • image — an image.
  • tool_use — assistant messages only. Claude asking you to run something.
  • tool_result — user messages only. You handing back what happened.

One message can mix several block types. Many plausible-looking loops break on that fact.

The response is an assistant message: role: "assistant", a content list of blocks, and a stop_reason saying why generation ended. Because it is already shaped like a message, you append it straight onto messages.

tools is a declaration, not an installation. Nothing runs on Anthropic's side: Claude emits a tool_use block and stops, you run the function, and you send the result back. Execution is local, and that is why Claude Code can show a permission prompt before a tool runs.

The API is stateless. There is no session and no server-side memory. Every request re-sends the whole messages array, and the model knows only what is in it. /compact rewrites that array.

One turn of the cycle

  1. Send system, the full messages array, and tools.
  2. Claude replies with an assistant message: text blocks, possibly tool_use blocks, and a stop_reason. The stop_reason, not the content, decides what happens next.
  3. If stop_reason == "tool_use", append the assistant message in full, run every requested tool, append one user message holding all the tool_result blocks, and loop.
  4. If stop_reason == "end_turn", stop. The text blocks are the answer.

The tool output you see indented in a Claude Code transcript is how it renders tool_result blocks. Memorise both shapes:

Field tool_use (assistant) tool_result (user)
type "tool_use" "tool_result"
identifier id — server-generated, e.g. toolu_01A… tool_use_id — must match the id character for character
payload name (tool name) and input (object matching the schema) content — a string, or a list of text/image blocks
failure signal — is_error: true, optional; the message goes in content

Pairing rules. The API enforces all three, and a violation returns a 400, not a degraded answer:

  • Every tool_use must be answered by a tool_result in the immediately following message. Return two results for three calls and the request is rejected.
  • Every tool_result needs a preceding tool_use with that id. This is what breaks when you truncate history to save context and the conversation ends up opening on a tool_result.
  • All results go in one user message, and the tool_result blocks must come first in its content. Any extra text goes after them.

Human-in-the-loop sits between tool_use and execution. Claude has asked, but nothing has run yet. That is where Claude Code's permission prompt lives. Approving runs the tool. Denying sends back a tool_result saying so.

def execute_tool(block):
    """Return a tool_result block for one tool_use block."""
    try:
        result = TOOL_IMPLS[block.name](**block.input)
        return {
            "type": "tool_result",
            "tool_use_id": block.id,
            "content": json.dumps(result),
        }
    except Exception as exc:
        return {
            "type": "tool_result",
            "tool_use_id": block.id,
            "content": f"{type(exc).__name__}: {exc}",
            "is_error": True,
        }


def run_agent(user_message, max_iterations=25, budget_seconds=120):
    messages = [{"role": "user", "content": user_message}]
    deadline = time.monotonic() + budget_seconds

    for iteration in range(max_iterations):
        if time.monotonic() > deadline:
            raise TimeoutError("wall-clock budget exhausted")

        response = client.messages.create(
            model="claude-sonnet-5",
            max_tokens=2048,
            system=SUPPORT_SYSTEM_PROMPT,
            tools=TOOLS,
            messages=messages,
        )
        log.info("iteration=%d stop_reason=%s", iteration, response.stop_reason)

        # The assistant message goes back verbatim, text blocks and all.
        messages.append({"role": "assistant", "content": response.content})

        if response.stop_reason == "tool_use":
            tool_uses = [b for b in response.content if b.type == "tool_use"]
            results = [execute_tool(b) for b in tool_uses]
            messages.append({"role": "user", "content": results})
            continue

            return response

        if response.stop_reason == "max_tokens":
            raise RuntimeError("response truncated; raise max_tokens")

        raise RuntimeError(f"unhandled stop_reason: {response.stop_reason}")

    raise RuntimeError("iteration cap hit — investigate, do not just raise it")

export async function runAgent(
  userMessage: string,
  { maxIterations = 25, budgetMs = 120_000 } = {},
): Promise<Anthropic.Message> {
  const messages: Anthropic.MessageParam[] = [
    { role: "user", content: userMessage },
  ];
  const deadline = Date.now() + budgetMs;

  for (let iteration = 0; iteration < maxIterations; iteration++) {
    if (Date.now() > deadline) throw new Error("wall-clock budget exhausted");

    const response = await client.messages.create({
      model: "claude-sonnet-5",
      max_tokens: 2048,
      system: SUPPORT_SYSTEM_PROMPT,
      tools: TOOLS,
      messages,
    });
    log.info({ iteration, stop_reason: response.stop_reason });

    messages.push({ role: "assistant", content: response.content });

    if (response.stop_reason === "tool_use") {
      const toolUses = response.content.filter(
        (b): b is Anthropic.ToolUseBlock => b.type === "tool_use",
      );
      const results = await Promise.all(toolUses.map(executeTool));
      messages.push({ role: "user", content: results });
      continue;
    }

    if (response.stop_reason === "end_turn") return response;
    if (response.stop_reason === "max_tokens") {
      throw new Error("response truncated; raise max_tokens");
    }
    throw new Error(`unhandled stop_reason: ${response.stop_reason}`);
  }

  throw new Error("iteration cap hit — investigate, do not just raise it");
}

The only branch is on stop_reason. The loop never inspects Claude's text, keeps no whitelist of which tool may follow which, and has no workflow state machine. Swap in Read/Bash/Edit/Grep, put a permission gate before execute_tool, and you have Claude Code's shape.

stop_reason is the control signal

Value Meaning What the loop does
"tool_use" The turn ended because Claude wants tools run. At least one tool_use block is present. Execute all of them, append results, iterate.
"end_turn" Claude finished naturally. No tools pending. Terminate; the text blocks are the answer.
"max_tokens" The response hit the max_tokens ceiling mid-generation and was truncated. Treat as an error condition. Any partial tool_use block is unusable — do not execute it.
"stop_sequence" Hit one of your stop_sequences. A requested stop. Treat like "end_turn".
"model_context_window_exceeded" Claude 4.5+: the context window filled mid-generation. Older models return a validation error instead. The conversation is too big. Trim or compact history; raising max_tokens won't help.

The exam focuses on "tool_use" (continue) and "end_turn" (terminate). Still handle unknown values in an explicit else that raises. A loop that falls through will one day treat a new stop reason as completion and return half an answer.

Strict tool use and thinking blocks

  • "strict": true next to a tool's input_schema makes schema-valid arguments guaranteed rather than merely very likely. The only cost is that one field. Chapter 3 covers the JSON Schema subset it supports.
  • Extended thinking: when a tool_use block sits alongside thinking or redacted_thinking blocks, send those thinking blocks back unmodified and in the same position on the next turn. Editing, reordering, or dropping one breaks its signature, and the request fails.

Why history is the agent's memory

Tool results are appended to history so the model can reason about the next action. That is how the agent accumulates knowledge, not a serialisation detail. In the support case:

  1. get_customer("dana@example.com") → history now holds customer_id: "cus_8812", tier: "enterprise".
  2. Claude reads that and calls lookup_order → shipped 19 days ago, inside a 30-day window.
  3. Claude calls process_refund with arguments it derived from history. You did not route them.

Ways to break it:

  • Drop the assistant message, keep the results. 400: a tool_result with no tool_use.
  • Keep the assistant message, drop the results. 400. If it somehow got through, Claude would re-request the same tool forever.
  • Summarise the result into your own prose. You have quietly become the decision-maker, filtering what the model can reason over.

All three treat history as a log when it is state. The same applies to /compact: whatever it drops, the agent no longer knows. That is why a long session "forgets" a decision from an hour ago.

Model-driven, not a decision tree

The exam contrasts Claude choosing the next tool from context with a pre-configured decision tree or fixed sequence. A fixed sequence (always get_customer → lookup_order → branch on amount) assumes every case has the same shape. Real cases don't:

  • Customer gives an order number → no email lookup needed.
  • Three disputed charges → three order lookups.
  • "Just let me talk to someone" → escalate_to_human, nothing else.

The loop above handles all of these with no routing code. You control the envelope: which tools exist, what their schemas allow, and which calls a hook may block (Chapter 6). Claude chooses within it. Plan mode is an example: it narrows the envelope to read-only tools, and Claude still decides everything inside it.

When ordering must be guaranteed, use a programmatic prerequisite gate (task 1.4, e.g. block process_refund until get_customer returns a verified id). Don't hard-code the call order in the loop.

tool_choice and how it bends the loop

Value Behaviour Loop impact
{"type": "auto"} (default) Claude decides whether to call a tool. Either stop reason is possible. This is the agentic setting.
{"type": "any"} Claude must call some tool, its choice which. Guarantees "tool_use" — the loop cannot terminate on this turn. Use it to stop the model answering conversationally when an action is required.
{"type": "tool", "name": "get_customer"} Claude must call that named tool. Also guarantees "tool_use", with the tool fixed.
{"type": "none"} Claude must not call a tool. Forces a text-only "end_turn".

Forcing applies per turn, not to the whole loop. Force get_customer on iteration one, then go back to auto. If you leave it forced, the loop can never reach "end_turn".

Parallel tool calls

One assistant turn can hold several tool_use blocks, for example two lookup_order calls for two disputed orders. It is the same as Claude Code firing three Reads at once. Run them concurrently (Promise.all, or asyncio.gather for slow I/O; the Python listing runs them sequentially for clarity) and return every result in one user message.

Claude parallelises only calls it believes are independent, and it can be wrong when one call's input should come from another's output. Safeguards:

  • State prerequisites in descriptions, e.g. "process_refund needs a verified customer_id from get_customer". This nudges the model to sequence the calls itself.
  • Gate the dependent tool programmatically when correctness can't rely on the model. A premature call then gets a structured error it can recover from.
  • disable_parallel_tool_use alongside tool_choice caps a response at one tool call. The cost is latency.

tool_use_id binds each result to its call. Keeping results in order is good hygiene but not required for validity.

Guardrails that are not termination logic

Only stop_reason decides that the task is complete. Separate operational guardrails decide that the loop is no longer allowed to run:

  • Max iterations bounds cost and catches cycles, such as retrying a tool that fails the same way every time. Exceeding it should raise, alert, and keep the transcript. Never return a partial answer as final.
  • Wall-clock budget covers what an iteration count can't. One slow MCP call can take 90 s inside a single iteration.
  • Structured logs record iteration, stop_reason, tool names, and durations, so an incident has a trace to read. Chapter 5 makes the same observability argument for routing subagent traffic through a coordinator.

Chapter 3 — Designing tools Claude can actually choose between

Claude Code picks Grep, Glob, and Edit reliably because its built-in tools are described with unusual care, not because selection is intrinsic to the model. Write two tools you think are obviously distinct and you may see coin-flip selection between them. The tempting explanations (the model is confused, you need a routing layer, add few-shot examples) are wrong. The exam's claim is causal: tool descriptions are the primary mechanism for tool selection, and minimal descriptions produce unreliable selection among similar tools.

What a tool definition actually is

Three fields: name, description, input_schema (a JSON Schema object). The model sees nothing else. Anything you know about the tool (which database it hits, what ID it needs, overlapping fields) is invisible unless it's in the description.

The description is prompt text. It is injected into context at selection time and read like any other instruction. It is not documentation for someone who can read the source. Treat it as an API contract and you'll write two lines where you needed twenty.

What a good description contains

Audit any description against five elements:

  1. What it does and returns: the shape of the result, not the implementation.
  2. Accepted input formats, including ones that look valid but aren't.
  3. Example queries in the user's language.
  4. Edge cases, especially "failed" versus "succeeded and found nothing".
  5. Boundaries against sibling tools, by name.

With near-neighbour tools, #5 outweighs the other four, because it's the only information the model can't infer from the tool in isolation.

Bad:

name: lookup_order
description: Retrieves order details.

Good:

name: lookup_order
description: >
  Look up a single order by its order number and return status, line items,
  fulfilment and delivery dates, carrier tracking, and the refund state of each
  line. Accepts an order number with or without the leading '#' (e.g. "#48812",
  "48812"). Does NOT accept email addresses, names, or account IDs.

  Use for queries like "where is my order 48812", "was #48812 delivered",
  "which items shipped in my last order".

  Use get_customer instead when the request identifies a person rather than an
  order ("look up my account", "what's on file for jane@example.com") or when
  you need the customer's order history rather than one order.

  If the order number is well-formed but not found, returns an empty result with
  found: false — this is a successful call, not an error, and usually means a
  typo or an order belonging to a different account.

What each part of the good version prevents:

  • Return description: the model no longer calls get_customer just to find out whether tracking data exists.
  • "Does NOT accept" clause: no email passed in, no turn burned on a validation error.
  • Example queries: they do the job of system-prompt few-shot examples, for fewer tokens, and they're maintained with the tool.
  • Boundary sentence naming get_customer: turns an overlap into a divide.
  • Empty-result note: stops the agent treating "not found" as a failure and retrying or escalating, when it should ask the customer to re-check the number.

150–250 tokens per description is normal, which is what Claude Code's own tools run to, and cheaper than a misrouted call plus the recovery turn.

strict: true guarantees the schema, not the selection

Descriptions fix which tool is called. A separate failure survives a perfect description: the right tool with a malformed argument, such as a string for a number or a missing required field. "strict": true beside input_schema constrains generation so the input matches the schema exactly, much as strict JSON output does in Chapter 13. Add it wherever a malformed input is costly (e.g. process_refund.amount_cents). It doesn't help selection, so a strict tool still needs a good description.

input_examples lets you attach example input objects as structured data. It is an alternative to writing example queries in prose, but prose still carries when to use the tool, which bare inputs don't.

Diagnosing misrouting

Misrouting has a signature: consistently the wrong member of a specific pair, on a consistent class of query. For example, get_customer gets called on order queries, or analyze_content and analyze_document (near-identical descriptions) are picked interchangeably regardless of input type.

Diagnose in order of cost:

  1. Compare the two descriptions. Could a new engineer, given only those strings, pick correctly for every failing query? If not, the descriptions are the cause.
  2. Check the schemas. If both take a bare string query, the schema offers no signal either.
  3. Only if the descriptions already discriminate, read the system prompt for keyword-sensitive instructions. "Always begin by understanding the customer" pulls calls toward get_customer whatever its description says. It overrides good descriptions and is invisible unless you look.

Non-fixes:

  • A deterministic routing layer that pre-selects tools from the input. It discards the model's language understanding and fails on every phrasing you didn't anticipate.
  • 5–8 few-shot examples in the system prompt. They add tokens to every request and leave the cause untouched. The model memorises surface patterns but still can't tell the tools apart.

The three repair moves

  1. Rename and rewrite to remove overlap. analyze_content becomes extract_web_results: it takes search snippets and URLs, returns passages with source attribution, and explicitly routes loaded documents to the document tools. The rename matters as much as the rewrite, because the name is what the model sees first.
  2. Split a generic tool into purpose-specific tools. If one tool does unrelated jobs, no description can fix it, because the ambiguity is in the tool. An analyze_document that summarises, extracts, or fact-checks depending on phrasing becomes extract_data_points, summarize_content, and verify_claim_against_source, each with defined I/O contracts and each naming the other two in its boundaries.
  3. Review the system prompt. It's the cheapest fix and the one most often skipped. Remove keywords that collide with tool names, and move real sequencing out of prose and into tool_choice or a programmatic prerequisite.

Naming: one convention across the inventory, snake_case verb plus resource, namespaced by service when there are several backends. billing_get_invoice and fulfilment_get_shipment are easy to tell apart; two get_records are not.

Distributing tools across agents

Selection reliability is a property of the tool set, not the individual tool. The exam's numbers: an agent with 18 tools selects less reliably than one with 4–5.

Agents also misuse tools outside their specialisation. Give a synthesis agent web search and it will search, because the tool is there and a gap seems to fit it. You get mediocre research instead of good synthesis, and blurred responsibility.

Default: scoped tool access, where each agent holds only what its role needs. In the research system:

  • Search agent: search and fetch tools.
  • Document agent: load_document plus the three extraction tools.
  • Synthesis agent: none of those.
  • Report agent: formatting and citation tools.
  • Coordinator: delegation tools only.

The verify_fact case. Strict scoping means synthesis must go through the coordinator to reach search, which adds 2–3 round trips and about 40% latency. Measurement shows 85% of verifications are simple (dates, names, statistics) and 15% need real investigation. Fix: give synthesis a limited, scoped verify_fact tool for the 85%, and keep routing the 15% through the coordinator. Wrong answers:

  • The full search toolkit for synthesis: over-provisioned, and it dissolves the separation of concerns.
  • Batching verifications to the end: later steps depend on earlier facts, so it creates blocking dependencies.

Same instinct for individual tools: replace generic with constrained. fetch_url (fetches anything) becomes load_document (validates that the URL is a document and rejects the rest).

The tool search tool, as an alternative to manual scoping

For an agent that legitimately needs many tools of one kind, the tool search tool (tool_search_tool_bm25_20251119 for keyword search, tool_search_tool_regex_20251119 for patterns) defers most definitions and lets Claude search for the relevant one on demand. It solves the context and selection-load problem, but not separation of concerns: a synthesis agent that shouldn't research still shouldn't have search. Scoping answers "who should be able to do this". Tool search answers "how do I keep a large legitimate inventory usable".

Chapter 4 — Errors, recovery, and telling the agent the truth

When a Bash command fails in Claude Code, Claude reads stderr, adjusts, and tries something else. No handler knows what command not found: uv means. Recovery works because the failure arrives as content the model can read, not as an exception that ends the turn.

In an agentic system, an error is a message to the model, and the model is its primary consumer, not the operator or the log. Raise an exception out of the loop and you remove the one participant that could narrow the query, try another source, or continue with what it has. Given "the pricing service did not respond within 30 seconds; this is usually transient", the model often plans recovery better than hand-written branches, because it holds the whole task in context. Backend reflexes like "fail fast" and "let it crash" are right for failures people read. They are harmful here, where failing fast kills the reasoning process that was about to solve the problem.

Two task statements share this material:

  • 2.2: structured error responses from MCP tools. The recipient is the calling agent.
  • 5.3: error propagation in multi-agent systems. The recipient is a coordinator handling a subagent that couldn't finish.

Both use the same taxonomy, the same access-failure versus empty-result distinction, and the same rule that partial results travel with the error.

Scope. Rate limits, quotas, and pricing are out of scope. Retry strategy is in scope as design judgement (attempt budgets, idempotency).

Layers not to conflate:

  • isError/is_error and the categories below cover your tool failing while the API is healthy.
  • overloaded_error (HTTP 529) and rate_limit_error (HTTP 429) mean the API call itself failed. They never reach the model as a tool_result. The SDK retries them beneath your loop with a small default budget, exponential backoff, and retry-after. Don't build a competing retry policy for this layer.
  • stop_reason: "model_context_window_exceeded" (Claude 4.5+) means the conversation ran out of room. Fix it by trimming or compacting history, not by retrying.

The two spellings of the same flag

A tool result is content plus one boolean saying "this is a failure":

  • MCP: isError on the tool result.
  • Messages API: is_error on a tool_result block.

isError is not a thrown exception. The tool returns normally with the flag set and a description. The model reads it as the outcome of its call, and the turn continues.

Protocol error Tool error
What broke The MCP server itself (malformed request, transport failure) The operation. The server worked fine.
Model sees it? Generally no Yes, via isError
Examples — Upstream payment failure, missing document, customer ID fails validation

Routing ordinary tool failures out as protocol errors, or letting an unhandled exception kill the turn, is the most common way to build an agent that can't recover from anything.

Four categories, one retryable

Category Typical cause Retryable What the agent should do
transient Upstream timeout, service unavailable, connection reset Yes Retry within a bounded budget, ideally inside the subagent; escalate only if the budget is exhausted
validation Malformed or out-of-range input, missing required field No Correct the arguments from the error description and call again with a materially different input
business Policy violation — refund window elapsed, item non-returnable No Stop, and explain the policy to the user in the customer-friendly terms the error supplies
permission Missing scope, expired credential, record outside the caller's tenant No Stop and escalate to a human or to a differently-scoped path; never loop

Only transient errors are retryable. Retrying the others fails the same way and wastes tokens and latency. "Not retryable" doesn't mean hopeless: after a validation error, the agent should call again with corrected input. That is a different act from a retry.

Guide inconsistency: the knowledge statements name four categories, but task 2.2's skills bullet lists errorCategory as only transient/validation/permission. Business-rule violations are instead described as the case needing retriable: false plus a customer-friendly message. Default to four categories, recognise the three-value list, and remember that retriable: false is attached to business violations by name.

Why "Operation failed" is the expensive answer

Generic, uniform error text is a named anti-pattern. If every failure reads Operation failed, the model can't tell a network blip from a policy refusal. Its only strategy is to retry, so it retries a refund that is out of policy on attempt one and still out of policy on attempt four. Structured metadata prevents wasted retries.

Payload shape:

  • errorCategory
  • isRetryable boolean
  • A description written for a reader who must decide what to do next
  • For business violations: retriable: false plus a customer-friendly explanation the agent can relay

Access failure is not an empty result

This appears in both Domain 2 and Domain 5.

  • Access failure: couldn't reach the data. It failed and needs a retry decision.
  • Valid empty result: reached the data, the query ran, nothing matched. That is a success and the answer is "none".

Collapse them and you lose information both ways. A timeout marked as an empty success produces a confident "no records" with no basis. An empty match marked as an error burns the retry budget re-asking an answered question. Make them structurally different, not just differently worded.

Local recovery, then honest escalation

The subagent is the right place to absorb transient failure. It is closest to the tool, knows expected latency, and retrying there costs the coordinator nothing. Handle transients locally and propagate only what you couldn't resolve, always with partial results and what was attempted.

Part Lets the coordinator…

What was attempted avoid reissuing the identical query

A web-search subagent times out mid-research. Correct: the four-part structured payload above. The distractors:

  • Retry with backoff, then return generic "search unavailable". The retry is fine and belongs there. The generic status is the defect: it throws away the queries tried and the data collected.
  • Catch the timeout, return an empty result marked successful. This suppresses the error, so no recovery is possible, and synthesis treats absence of findings as evidence of absence.
  • Terminate the workflow from a top-level handler. Honest but disproportionate: it kills the whole run when a narrowed retry or another source would likely have worked.

The last two are task 5.3's named anti-patterns: suppressing errors as empty success, and terminating an entire workflow on one subtask failure.

Coverage annotations: partial is fine, undisclosed is not

Synthesis output must mark which findings are well supported and which topic areas have gaps because sources were unavailable. "Competitor pricing: three independent sources; regulatory outlook: no sources retrieved, all queries timed out" is useful. The same report with the regulatory section silently dropped is a hazard, because the reader can't tell "investigated, found nothing" from "never reached".

Partial results are acceptable. Undisclosed partial results are not.

Idempotency, and the refund you paid twice

process_refund posts the refund, then the response times out. The tool correctly reports a retryable transient error, the agent retries, and the customer is refunded twice. The category was right, but the operation wasn't safe to retry.

Retryability is a property of the operation as well as the error. Make mutating tools idempotent: the client supplies a key derived from the request's intent, not the attempt, and the server returns the original outcome for a repeated key.

Make the key a required schema parameter and describe it as identifying the refund attempt, so the model reuses it on retry. The caller is a model choosing arguments from prose, so the description is all that stands between you and a duplicate payment. A key regenerated per call protects nothing.

Retry strategy as a design decision

  • Exponential backoff with jitter for transients. Backoff gives the dependency room to recover. Jitter stops parallel subagents retrying in lockstep (thundering herd).
  • Bound attempts: 2–3 when a human is waiting, more for batch.
  • Retries the model sees cost tokens. Each failed attempt stays in context for the rest of the session, crowding out useful material. Absorb retries inside the subagent and surface one summarised outcome.
  • Set a per-turn budget alongside the per-call one. When it's exhausted, escalate with the four-part payload.

Chapter 5 — Orchestration

When Claude Code fans a broad request out to subagents, it is running a small distributed system. A coordinator decides to delegate, isolated workers each see only what they are told, and a synthesis step reconciles results that never talked to each other. This chapter covers building that system yourself with the Agent SDK (task statements 1.2 and 1.3), so you can diagnose it and use it where no Claude Code exists.

Running example: the exam's Multi-Agent Research System. A coordinator delegates to search and document-analysis subagents, and a synthesis subagent writes the report. Customer support is the secondary example.

Why orchestration is a separate problem from the loop

Chapter 2's loop is one agent with one growing messages array. Orchestration applies when one context is the wrong shape for the whole problem:

  • Tool load: 18 tools select worse than 4–5, and out-of-specialisation tools get misused (Chapter 3). One agent holding search, document loading, extraction, and formatting will sometimes half-read a document instead of delegating.
  • Context load: a single conversation accumulates every document, result, and draft, so by synthesis time the signal is buried. Separate bounded contexts are a context-management technique as well as a division of labour (Chapter 14).

Hub-and-spoke: the coordinator owns everything

Default architecture: one coordinator at the centre. Subagents talk only to the coordinator, never to each other. The coordinator decomposes, delegates, and aggregates. A finished search subagent returns to the coordinator, which decides what synthesis sees.

Giving up direct subagent-to-subagent communication buys three things the exam names:

  1. Observability: everything passes through one place, so one log tells the whole story.
  2. Consistent error handling: one place decides whether to retry, substitute, or surface partial results.
  3. Controlled information flow: the coordinator can filter, summarise, or redact before passing data on, e.g. keep sensitive document content away from the report agent.

In support: a case needing order history and a fraud check before process_refund routes both through a coordinator, not a fraud agent reading the order agent's output directly. One place sees the case and decides what an inconclusive fraud check means.

Subagents have no memory of the coordinator, or of each other

A subagent's context is isolated. It does not inherit the coordinator's history, and separate invocations of "the same" subagent share nothing. The Task tool starts a subagent with only the prompt you write. Anything the coordinator or an earlier subagent learned exists for it only if it is in that prompt.

The exam's example: a synthesis subagent prompted with just "Synthesize the research findings into a report." It has no findings, because they live in the coordinator's history, so the output is generic and uncited. The fix is to put the findings in the prompt, not to use a bigger model or give synthesis a WebSearch tool. That would move research into the wrong agent and break separation of concerns.

The Task tool looks like any tool (name, description, schema), but calling it starts a new agentic loop with its own messages array and returns that loop's final result as the tool result. Claude Code spawns its subagents this way.

Resuming a subagent

A Task/Agent result carries a session_id (surfaced as agentId in current tooling) for that subagent's transcript. Pass it back as resume: sessionId on a later Task call to continue that subagent's history instead of starting from nothing. This helps when a document subagent has built up expensive context on a document set. Resume when the prior context is still valid and worth its cost; otherwise spawn fresh (the same judgement as Chapter 7).

Spawning in parallel: multiple Task calls, one turn

Parallel delegation = multiple Task calls in a single coordinator response. Four Task calls in one turn run four subagents side by side. One per turn over four turns runs them in sequence, at much higher wall-clock cost, since each is its own multi-step loop.

There is no parallelism flag. Distractors offer real parameters that govern something else, e.g. disable_parallel_tool_use, which controls batching of ordinary tool calls in a turn.

With query(), the SDK harness sees the four tool_use blocks and runs the four loops concurrently. You supply options and read typed messages.

Partitioning scope without narrowing the topic

Splitting "creative industries" into visual arts, music, writing, and film/video partitions scope correctly: no duplication, and full coverage. The exam calls this partitioning research scope to minimise duplication: assign each subagent distinct subtopics or source types (e.g. one agent on regulatory filings, one on news, one on vendor pages).

Now split it into gallery representation, digital art marketplaces, and museum curation, which are all visual arts. Every subagent succeeds with well-cited findings. Synthesis faithfully produces a confident report covering about a quarter of the topic. Nothing errored, every log is green, and the answer is wrong.

When every subagent succeeds and aggregate coverage is still wrong, the defect is in the coordinator's decomposition. Error handling can't catch it. You catch it only by comparing the decomposition against the original question's breadth, before delegating and again after synthesis.

Iterative refinement: the coordinator checks its own coverage

A one-pass pipeline (decompose → delegate → synthesise) can't catch narrow decomposition after the fact. Make it a loop: evaluate synthesis for gaps against the original question, re-delegate targeted queries for the gaps, re-synthesise, and repeat until coverage is sufficient.

Python

def run_research_coordinator(question, max_refinement_rounds=3):
    findings = delegate_initial_research(question)   # parallel Task calls
    report = invoke_synthesis(question, findings)

    for round_num in range(max_refinement_rounds):
        gaps = evaluate_coverage(question, report)    # coordinator's own check
        if not gaps:
            return report
        log.info("refinement round=%d gaps=%s", round_num, gaps)
        targeted_findings = delegate_targeted_research(gaps)  # more Task calls
        findings = findings + targeted_findings
        report = invoke_synthesis(question, findings)

    report["coverage_warning"] = (
        "Refinement rounds exhausted; known gaps may remain unresolved."
    )
    return report

evaluate_coverage must look for named subtopics that never got a subagent, not just check for non-empty output. The three visual-arts subagents all returned good, non-empty results. The loop is bounded and warns loudly when exhausted. It never silently returns incomplete work as complete.

Query complexity: not every question needs the full pipeline

The opposite failure is over-processing. "What year was [a well-known data regulation] enacted?" doesn't need search, then document analysis, then synthesis. The coordinator's prompt should have it assess complexity first (simple lookup, comparison, or open investigation) and invoke only the subagents needed. Left at "always run the full team", it spends four invocations on a one-agent question. In support, a plain order-status request doesn't need a fraud check.

Fork-based sessions, briefly

Forking branches a session into independent copies from a shared baseline, so you can explore two divergent approaches (e.g. two report framings) without re-deriving the shared analysis. It is a session mechanism, covered in Chapter 7.

Scaling past hub-and-spoke, and the default subagent

  • Workflow tool (separate from Task/Agent) orchestrates dozens to hundreds of agents outside the coordinator's conversation. Hub-and-spoke keeps everything in the coordinator's context, which is what buys observability and controlled flow, and that context would overflow at large scale. They answer different problem sizes. Hub-and-spoke still applies at small to moderate scale.
  • general-purpose is a built-in subagent always available even with no agents defined, unless disabled with CLAUDE_AGENT_SDK_DISABLE_BUILTIN_AGENTS=1. A coordinator with an empty agents map can still delegate.

Chapter 6 — Hooks and gates

Claude Code's permission prompt is an architectural pattern. The model emits a tool_use block, and before the call reaches the real world, code outside the model inspects it and can refuse. Nobody asked Claude nicely not to run rm -rf. The loop was stopped at a point the model has no say over.

This is arguably the highest-yield idea on the exam: prompt instructions have a non-zero failure rate. However carefully you write "always verify the customer before refunding", enough conversations, context pressure, and adversarial phrasing will produce some runs that refund anyway. An instruction competes with every other token for attention. A gate doesn't compete: it runs, checks, and returns a fixed answer.

In the support scenario, most decisions (which order, which policy, what to say) are fine left to the model. Two properties must never be false:

  1. A refund is never issued against an unverified identity.
  2. A refund never exceeds the policy threshold without a human.

Claude Code's hook system exposes the two seams: PreToolUse (before a call executes) and PostToolUse (after a result returns). The permission prompt is a PreToolUse hook with a UI. This chapter builds both seams by hand, because the exam tests the pattern, not the config file (Chapters 9–10 cover that).

The enforcement ladder

Mechanism What it constrains Scope Guarantee
System prompt instruction What the model is told to prefer Every turn, informally None — the model can be wrong or overridden by competing context
tool_choice forcing Which tool the next response must call One request Strong, but only for a single turn
Programmatic gate or hook Whether a call is allowed to execute, or what a result looks like once it returns The whole session, or however long your code holds the state Absolute — the check runs in your process, not the model's

The exam's trap: forcing get_customer guarantees only that the next response calls it. Three turns later you're back on "auto", and nothing stops an unverified process_refund. A prerequisite across an open-ended conversation must live in code that persists and inspects every call. That is a gate.

When to use deterministic enforcement: the consequence is financial, compliance, or security, or an ordering must never be skipped (identity before payment is the canonical case). Below that tier, a good prompt is fine, and a hook is a mistake (see the counterweight below).

Prerequisite gates: blocking the call, not asking nicely

A prerequisite gate sits between the model's request and execution and refuses the call until an earlier condition holds. The exam's instance: block process_refund until get_customer has returned a verified customer ID. It's a dict lookup and an if, but three details matter:

  1. State is per conversation, not process-global. One shared boolean across concurrent sessions lets session B refund on session A's verification. That fails silently and looks like success, which is worse than no gate. Key the state by conversation ID.
  2. Return, don't raise. A raised block kills the loop like any uncaught exception (Chapter 4). Return a normal tool_result with is_error and a description of what's missing, and the model recovers: it calls get_customer, then retries.
  3. Gate the mutation, not neighbouring reads. Gating lookup_order as well gains no safety and stops the agent answering "what's in my order?" for the majority of contacts that never refund. A sample question offers "gate both lookup_order and process_refund" as a wrong answer because it is disproportionate, not unsafe.

Python

Direction is not a detail: interception versus PostToolUse

This is an easy distractor, because the two look alike in a diagram:

  • Interception (PreToolUse, pre-call) inspects a call before dispatch and can block it.
  • PostToolUse inspects a result after it returns. The action has already happened.

Once process_refund returns, the money has moved. PostToolUse can log, flag, or page, but it can't un-refund. "Refunds over $500 never go out without a human" can only live before the call, in interception.

Python

PostToolUse: normalizing what comes back

PostToolUse solves data quality, not compliance. Real support tooling spans systems: lookup_order returns Unix epoch timestamps, get_customer returns ISO 8601, a third returns status codes 0/1/2 with the meaning in an unattached lookup table. Making the model translate formats as a side job is the kind of mechanical task a probabilistic reader gets wrong on the odd input.

A PostToolUse hook rewrites every result into one shape (field names, date format, status vocabulary) before the model sees it.

Python

from datetime import datetime, timezone

STATUS_CODES = {0: "active", 1: "suspended", 2: "closed"}

def normalize_tool_result(tool_name: str, raw: dict) -> dict:
    result = dict(raw)
    if tool_name == "lookup_order" and isinstance(result.get("ship_date"), int):
        result["ship_date"] = datetime.fromtimestamp(
            result["ship_date"], tz=timezone.utc
        ).date().isoformat()
    if tool_name == "get_customer" and isinstance(result.get("status"), int):
        result["status"] = STATUS_CODES.get(result["status"], "unknown")
    return result

TypeScript

const STATUS_CODES: Record<number, string> = { 0: "active", 1: "suspended", 2: "closed" };

function normalizeToolResult(toolName: string, raw: Record<string, unknown>) {
  const result = { ...raw };
  if (toolName === "lookup_order" && typeof result.ship_date === "number") {
    result.ship_date = new Date(result.ship_date * 1000).toISOString().slice(0, 10);
  }
  if (toolName === "get_customer" && typeof result.status === "number") {
    result.status = STATUS_CODES[result.status as number] ?? "unknown";
  }
  return result;
}

Wire it into execute_tool from Chapter 2: call the tool, normalise, then serialise into content.

Agent SDK names (task 1.5 is phrased in SDK terms):

  • PreToolUse callback returns hookSpecificOutput with permissionDecision ("allow", "deny", "ask", "defer") and permissionDecisionReason. It can rewrite arguments via updatedInput instead of blocking.
  • PostToolUse callback returns additionalContext to append, or updatedToolOutput to replace the output before Claude sees it. That is the SDK capability behind normalisation.

Why a hook rather than "dates may be Unix or ISO; interpret carefully" in the prompt? The prompt usually works but spends tokens every turn re-deriving a fixed fact. And if lookup_order is a third-party MCP server, prompting the model can't change what it returns. You can only change what the model is shown. The hook converts once, and every turn gets clean data.

The counterweight: not every rule needs a hook

Hooks are code: they have bugs, need maintenance, and add failure seams. For soft preferences (phrase refunds politely, prefer store credit, mention the loyalty programme), a prompt is adequate, misses are cheap, and a hook is over-engineering.

Test: does a probabilistic miss justify code that can never be skipped? Money, skipped identity checks, compliance: yes. Tone, phrasing, a choice between two acceptable orderings: no. Over-gating brings back the rigidity of the decision trees criticised in Chapter 2.

Multi-concern decomposition: one customer, several problems

"SO-44120 arrived damaged, and I was also charged twice for last month's subscription" is two concerns in one message. Named failures:

  • Resolving one and telling the customer to open a second ticket.
  • Handling independent concerns serially.

Both hurt first-contact resolution, the scenario's headline metric.

Correct pattern: decompose into distinct items, investigate in parallel on shared context, and synthesise one unified resolution. Shared context means fetching the customer once and passing the same verified customer_id to both branches, not having each call get_customer (and re-verify through the gate). The two lookups are independent once the customer is known, so they can be parallel tool_use blocks.

Chapter 7 — Sessions

You resume a two-day-old Claude Code session and Claude confidently describes a file you rewrote yesterday. It isn't hallucinating. It is reading its memory correctly, but the memory is old. Task statement 1.7 is about the gap between "history is intact" and "history is true": when to resume, when to fork, and when resuming is worse than starting over.

What a session actually is

A session is the running list of blocks: user turns, the model's text and tool calls, and the tool_result blocks that came back. It is replayed to the model every turn. Resuming reloads that list. It revalidates nothing. Every tool result in it is treated as still describing the world.

That's what lets a resumed refactor remember the plan and naming decisions. It is also a cache, and it is only correct if the world hasn't moved since it was written.

Resuming a named session

The skill: --resume <session-name> to continue a specific investigation, not just the latest one, because you usually have several lines of work going.

Example: on Monday Claude explored a legacy billing module, designed a split of process_refund out of a monolith, and started the new module. On Tuesday, if nothing changed overnight, resuming is clearly right, and re-deriving it would be waste.

What the exam tests is the condition, not the flag: resume when prior context is mostly still valid.

resume versus continue

resume continue
SDK form Python resume=<session_id> TS continue: true; Python continue_conversation=True
Takes an id? Yes No
Picks up Exactly the named session Whatever was most recent in the current directory
Scenario wording "a specific investigation from earlier" "the most recent session"

With several lines of work in one project, continue may pick the wrong one.

When resuming lies to you

Overnight, a teammate rewrote six files in the auth module your session analysed. You resume. The transcript still contains Monday's contents and analysis verbatim, and nothing marks them as stale. Forking: one baseline, divergent explorations

fork_session answers a different question: you've paid for a shared baseline and want to explore several paths from it without them polluting each other, and without paying for the baseline twice.

Example: Claude has mapped a service's test setup (fixtures, mocks, flaky spots). Two strategies, "migrate to contract tests" and "add property-based tests", both need that map and then diverge.

  • Both in one session: strategy A's dead ends stay in context and warp reasoning about B.
  • Two fresh sessions: no pollution, but the careful exploration is repeated or reduced to a summary.
  • fork_session: each branch inherits the full baseline once, then diverges in isolation.

The research scenario is the same: fork after the shared literature review into a regulatory branch and a pricing branch.

Forking is a resume with a flag: point at the baseline id and branch rather than continue.

Situation Right mechanism Why
Continuing one investigation, prior context still holds --resume <session-name> Reuses valid context at no cost
Continuing one investigation, a known subset of files changed --resume, plus an explicit list of what changed Targets re-analysis instead of trusting stale results or re-exploring everything
Continuing one investigation, most tool results are stale or unenumerable Fresh session seeded with a structured, hand-verified summary Avoids re-presenting decayed tool output as current fact
Comparing two or more approaches from one shared baseline fork_session Keeps the full baseline once, isolates each branch's exploration from the others

What the exam tests

Task 1.7 stems ask you to pick one of the four rows above.

  • A handful of files changed: resume and name the files. Traps: resume silently (stale results read as current), or discard everything (throws away valid context to fix a narrow problem).
  • Broad staleness (long gap, wide crawl, external data): fresh session with an injected summary. A targeted note isn't enough because there's no small list to give. Know the reason: resumed tool_results carry no marker of decay.
  • "Compare" / "divergent approaches" from "the same starting point": fork_session. Traps: repeated --resume into one transcript, or duplicated fresh sessions that discard the baseline.

Chapter 8 — MCP

As a consumer, MCP looks like a plugin system: add a config entry, get new tools. The exam wants the layer above that: what goes in the config, who else sees it, and whether a tool should exist at all.

MCP standardises the interface between an agent and an external capability. Before it, every agent needed its own bespoke integration for each tool. Now one GitHub server works identically from Claude Code, an Agent SDK app, or another host.

Scope of task 2.4: configuration, scoping, discovery, descriptions, build versus buy. Out of scope: transports (stdio vs network), hosting, containers, load balancing, OAuth. Answer options mentioning those are decoration on a wrong answer.

What MCP actually standardizes

Primitive What it is Example
Tools Actions that do something or fetch a specific known thing Jira search_issues, create_issue
Resources Read-only content to browse A docs table of contents, a label taxonomy
Prompts Reusable prompt templates shipped by the server Rarely used in Claude Code workflows. Just know it exists

Resources are for catalogs; tools are for actions. A resource fixes a specific reliability problem: an agent that doesn't know what exists will guess and call tools speculatively.

  • Issue tracker: without a resource, the agent calls search_issues 2–3 times with guessed keywords just to learn which components and labels exist. A resource exposing the label taxonomy, component list, or open-epic summary lets it read once, then make one targeted call.
  • Document store: a resource exposing folder hierarchy and titles stops repeated list_documents calls at different prefixes.

You won't implement resources by hand for the exam. You need the judgement: content the agent browses to orient itself is a resource, and things that act are tools.

Scoping: local, project, and user

Scope decides who shares the configuration, nothing about inference.

Project .mcp.json at repo root, committed Everyone who clones Team workflow tooling a new hire should have on day one

The model picks among them per turn, just as it picks between Grep and Glob. A question where a project server "takes priority" over a user server, or hides it, describes something that doesn't happen.

One narrow exception, which the exam doesn't test: when two scopes define a server with the same name, Claude Code resolves the collision with a fixed precedence (local → project → user → plugin → claude.ai connector) and connects once. That is scope resolution. Tool selection stays priority-free.

Build versus buy

  • Standard integrations (Jira, GitHub, Slack, Drive, common DBs): use an existing community or vendor server, configured at project scope with env-expanded tokens. Someone has already handled pagination, custom-field mapping, rate limiting, and the API edge cases that only show up after months across many installations. A home-grown one handles what you tested and silently breaks on the rest.
  • Team-specific workflows: build custom. Examples: one tool wrapping three internal systems, a resource exposing your own document taxonomy, business rules such as which refund reasons need a supervisor or which labels auto-escalate. A generic server can't know your rules exist. You also then own description quality from scratch, which is one more reason not to build by default.

Keep the question types apart. Scope and priority are configuration facts with one answer each. Build-vs-buy and description quality are judgement calls that depend on the scenario.

What the exam tests

  • Scope recall: project .mcp.json (shared) versus user ~/.claude.json (personal/experimental), plus env var expansion. The wrong answer hardcodes a token in a committed file.
  • Scope ≠ priority: with both scopes configured, every server's tools are discovered at connection time and sit together in one inventory, with no scope-based priority.
  • Resources vs tools: an agent burning calls on exploratory discovery of a content catalog (issue summaries, doc hierarchy, schema) needs a resource, not a new tool or a bigger prompt.
  • MCP tool loses to Grep: enhance its description. Don't change scope, restrict the built-in, or add a routing rule.
  • Build vs buy: standard integration means a community server. Custom is only for team-specific needs.
  • Transports, hosting, and OAuth are out of scope.

Chapter 9 — Configuring Claude Code

You already use CLAUDE.md. This chapter gives you the exam's vocabulary for it (task statements 3.1 and 3.3): which file wins, what "shared" means at each level, and the sharpest distinction in the domain. A rule can load because of where a file sits (directory-bound) or because of what kind of file it is (type-bound, via glob). Test files interleaved across 40 packages have no directory whose boundary is "every test file". No directory layout solves that. A glob in .claude/rules/ does.

Slash commands, skills, and plan mode are in Chapter 10.

The CLAUDE.md hierarchy

Level Path Shared? Scope
Managed/enterprise policy macOS /Library/Application Support/ClaudeCode/CLAUDE.md; Linux/WSL /etc/claude-code/CLAUDE.md; Windows C:\Program Files\ClaudeCode\CLAUDE.md Org-enforced. Can't be deleted or excluded Loads first
User ~/.claude/CLAUDE.md No. Your home dir, never in git Every project you touch
Project .claude/CLAUDE.md or root CLAUDE.md (both valid) Yes. Committed, reaches every clone and CI job This repo

User, project, and directory are the three the exam leans on. CLAUDE.local.md suits personal-but-repo-specific preferences, like "I run this repo's tests with -k slow".

The key property is who sees the file. Project-level is for anything the team must follow. User-level is for your own preferences (commit verbosity, explain-before-code) and is never right for team conventions.

The diagnostic the exam tests most: a new engineer clones the repo and half the team's conventions don't apply for them. The conventions live in the tech lead's ~/.claude/CLAUDE.md, written as personal habit and never promoted. Engineers who copied a senior's dotfiles inherited them by accident. The fix is always to move the content from ~/.claude/CLAUDE.md to the project file. Not more docs, not an onboarding checklist. "Works for me but not for the team" means this misplacement.

Directory-level handles conventions for one subtree. A monorepo keeps org-wide conventions at root, DB access patterns in services/billing/CLAUDE.md, and component conventions in apps/web/CLAUDE.md. Each loads only when work touches its subtree. It activates on location.

Modular organization: @import and .claude/rules/

Two separate tools for breaking up a monolithic CLAUDE.md. The exam tests them as distinct facts.

@import pulls an external file into a CLAUDE.md by path. The package maintainer picks which standards apply:

# services/billing/CLAUDE.md

This service handles payment processing and refund issuance.

@docs/standards/python-style.md
@docs/standards/api-design.md

Refunds above $500 require the process_refund tool's manual-review path;
see the runbook in docs/refunds.md before touching that code path.

A Terraform-only package imports terraform-conventions.md instead and never loads the Python guide. The judgement sits with whoever knows the package.

  • AGENTS.md interop: Claude Code reads CLAUDE.md, not AGENTS.md. Use @AGENTS.md inside a CLAUDE.md, or a symlink, rather than maintaining two drifting files.
  • claudeMdExcludes (settings.json, any layer, arrays merge) excludes CLAUDE.md or rules files by glob on absolute paths. Use it to stop a subpackage inheriting a rule without moving the rule file.

.claude/rules/ splits one file doing too many jobs into topic files (testing.md, api-conventions.md, deployment.md), each small enough to own and review.

.claude/

  rules/
    testing.md           # pytest conventions, fixture policy
    api-conventions.md   # REST error shapes, versioning policy
    deployment.md         # rollout steps, rollback procedure

Without frontmatter these always load. It is just organisation. With paths frontmatter (below), they load conditionally.

Diagnosing with /memory and /context

Instructions come from several levels, imports, and rule files, so "why did Claude do that?" needs tooling:

Exam answer: /memory verifies which memory files are loaded and diagnoses inconsistent behaviour across sessions. That is the guide's wording for task 3.1, and /context appears nowhere in the guide.

Current Claude Code differs. /memory now lists and opens CLAUDE.md and rules locations (including ones not yet created) and toggles auto memory. In your own work, check /context first, then use /memory to open the file and find out why (wrong level, stale @import path, non-matching glob). On the exam, answer /memory.

Path-specific rules: scoping by file type, not by location

A .claude/rules/ file with YAML frontmatter paths: (a list of globs) loads only when the file being edited matches.

---
paths: ["terraform/**/*"]
---

# Terraform conventions

All resources must be tagged with `team` and `cost-center`. Modules under
terraform/modules/ are versioned by git tag, not by branch — never reference
a module by branch name in a `source` argument. Run `terraform fmt` before
every commit; CI will reject unformatted plans.

Mechanics:

  • Rules are discovered recursively (.claude/rules/frontend/testing.md works) and can be symlinked in, so one rule can be shared across repos.
  • ~/.claude/rules/ applies to all your projects and loads before the project's .claude/rules/. The project rule wins on conflict.
  • Brace expansion works (**/*.{ts,tsx}), capped at 1000 expanded patterns and 4 MiB.

That Terraform example is directory-shaped, so a directory CLAUDE.md could also express it. The case only a glob can express is file type scattered across locations, which is the exam's sample question 6:

Button.tsx sits next to Button.test.tsx, and useAuth.ts next to useAuth.test.ts, across 40 component directories. You want one test rule: use the custom render wrapper, follow arrange-act-assert comments, mock the API client uniformly.

  • Root CLAUDE.md: the rule applies to components and tests alike, written as an "if this is a test file" aside. The model has to infer scope from prose.
  • CLAUDE.md in each directory: 40 copies, no single source of truth, and the rule is still keyed to address rather than suffix.
  • Glob rule: scopes on the filename shape.
---
paths: ["**/*.test.tsx", "**/*.test.ts"]
---

Use `renderWithProviders` from src/test-utils, never the raw `render` export
from the testing library — our components depend on theme and auth context

assert, with a blank line between each section. Mock the API client via

Editing any *.test.tsx anywhere loads it.

Scoping question Right mechanism Why
"Everyone on the team needs this instruction." Project-level CLAUDE.md (.claude/CLAUDE.md or root CLAUDE.md) Committed to version control, reaches every clone.
"Only I want this instruction, on every project I touch." User-level CLAUDE.md (~/.claude/CLAUDE.md) Personal, never shared, not version-controlled.
"This convention applies to one subtree and nowhere else." Directory-level CLAUDE.md Directory-bound: loads based on where the edited file lives.
"This convention applies to a file type, wherever it appears in the tree." .claude/rules/*.md with a paths glob Type-bound: loads based on what the edited file is, regardless of location.

"This file is too big; I want to split it by topic without changing when anything loads." Plain files under .claude/rules/ (no paths frontmatter) Organizational split; always loaded, just not monolithic.

Token economy (the second half of 3.3): conditional loading keeps Terraform rules out of context while you edit React, and the reverse. A comprehensive root CLAUDE.md carries everything on every turn.

Distractors for the scattered-tests scenario:

  • "Consolidate into root CLAUDE.md with a testing section." Relies on the model inferring scope from prose. There is no mechanical match, so the advice can leak into non-test files or be missed in a long file.
  • "Put it in a skill." Skills are invoked on demand, by command or by the model's judgement. A convention that must apply automatically every time can't depend on invocation.

Path rules are automatic (unlike skills) and location-agnostic (unlike CLAUDE.md). That combination is why they exist.

Choosing between subdirectory CLAUDE.md and glob rules

If the boundary is a place in the tree, use a subdirectory CLAUDE.md. If it is a kind of file that appears in many places, use a glob rule.

Convention Varies by Mechanism
"This service talks to Kafka differently" Location Subdirectory CLAUDE.md
"Every .tf file gets tagged the same way" Type Glob rule
"Never hand-edit src/generated/" Location Subdirectory CLAUDE.md

They compose: a thin root CLAUDE.md for orientation and org policy, directory files for the few location-bound conventions, and glob rules for type-bound ones (tests, migrations, generated-code markers, IaC).

  • CLAUDE.md: conventions you guarantee, reviewed and versioned.
  • Auto memory: what Claude learned about how you work (terse commits, a refactor already rejected, who owns deploys).

Chapter 10 — Extending Claude Code

Two halves (task statements 3.2 and 3.4). Slash commands and skills make a prompt durable and shareable: a file, version-controlled, identical every time. Plan mode decides whether a task needs a design phase before any edit. You've used both. The exam wants the exact mechanism (file, directory, frontmatter field) and the ability to pick the right one from a task description.

Slash commands: where the file lives decides who gets it

A custom slash command is a markdown file whose body becomes the prompt, and its filename is the invocation. There is no registration step.

Location Scope Reaches
.claude/commands/ in the repo Project Every teammate on clone or pull, via version control
~/.claude/commands/ User Only you, across all projects

"/review must run the same way for every developer on clone": the answer is .claude/commands/. Distractors:

  • Put it in CLAUDE.md. CLAUDE.md carries context and standards, not invocable actions.
  • A registration file listing commands. None is needed. The file's presence is the registration.

Personal shorthand that shouldn't reach teammates goes in ~/.claude/commands/.

.claude/commands/review.md          # project-scoped — every teammate gets /review
~/.claude/commands/my-triage.md     # user-scoped — only you get /my-triage

Skills: commands that carry configuration

A skill is a command plus frontmatter that Claude Code enforces around the invocation. Current Claude Code treats them as one mechanism: .claude/commands/foo.md and .claude/skills/foo/SKILL.md both give /foo, and a skill is the superset.

Locations and precedence:

  • Enterprise/managed: org-controlled, applies to everyone.
  • Personal: ~/.claude/skills/<name>/SKILL.md.
  • Project: .claude/skills/<name>/SKILL.md, shared via git.
  • Plugin: <plugin>/skills/, invoked as plugin:skill to avoid name collisions.
  • Nested project dirs: apps/web/.claude/skills/deploy/ is invoked as /apps/web:deploy, so frontend and backend deploy skills can coexist in a monorepo.

The three exam fields:

Field Does Use when
argument-hint Prompts the developer for a missing argument when invoked bare The skill can't work without, e.g., a service name or ticket. Otherwise it guesses or fails silently
allowed-tools Restricts tools during skill execution (the guide's framing) The skill must not be able to delete or run arbitrary shell. E.g. release notes: read plus file-write only
context: fork Runs the skill in an isolated sub-agent context. Only the result returns to your conversation The skill is verbose (reads dozens of files for a 3-paragraph summary) or exploratory (brainstorming whose discarded options would bias later turns)
  • Caveat on allowed-tools, for real use and not the exam: current docs define it as tools usable without asking permission, a pre-approval, not a fence. The field that removes tools is disallowed-tools. On the exam, allowed-tools restricts tools. In your repos, use disallowed-tools for the guarantee.
  • context: fork is the mechanism that keeps a skill's internal noise out of your transcript. You get the conclusion without the scaffolding.
---
name: analyze-refund-patterns
description: Scans recent process_refund calls for anomalies and reports a summary.
context: fork
allowed-tools: Read, Grep, Glob
argument-hint: "[date-range, e.g. 2026-08-01..2026-08-31]"
---

The body after the frontmatter is plain markdown. Skills are not a templating language.

Who may invoke a skill:

  • disable-model-invocation: only a human can trigger it, never the model on its own judgement. Use it for side effects like /deploy.
  • user-invocable: false: hidden from the command list, so the model invokes it automatically. Use it for background-knowledge skills.
  • paths frontmatter: same glob scoping as .claude/rules/. The skill is considered for auto-invocation only when the current file matches.

Other frontmatter exists and isn't tested: when_to_use, arguments/$name, model, effort, background, agent, hooks, shell, metadata, license, compatibility.

Bundled skills (/doctor, /code-review, /run, /verify, /loop, /debug, …) ship out of the box. disableBundledSkills and skillOverrides turn them off or replace them.

Personal variants without stepping on teammates

To get different behaviour from a shared skill, create a second skill under a different name in ~/.claude/skills/. The project has .claude/skills/extract-invoice/SKILL.md, and you want currency normalisation too, so create ~/.claude/skills/extract-invoice-mine/SKILL.md. The shared skill is untouched and teammates are unaffected. The exam's answer is always rename-and-relocate, never an in-place edit of the shared file.

Skills versus CLAUDE.md

The test is not importance but whether the content applies to every interaction or only to one nameable task:

  • CLAUDE.md: universal standards loaded every turn, e.g. the commit message convention.
  • Skill: an on-demand, task-specific workflow, e.g. auditing process_refund call sites for compliance. Loading that every turn is pure context cost.

"Should apply always, to everyone, unasked" is a CLAUDE.md question dressed as a skills question.

Plan mode versus direct execution

The exam tests whether you can tell from the task description, before any exploration, whether plan mode was needed.

Plan mode gives safe exploration plus a human-reviewed design before any file changes. It prevents rework from committing to the wrong shape of change. Use it when there are several legitimate approaches and a wide blast radius. Canonical cases:

  • Monolith → microservices.
  • Migrating 45 files to a new library version.
  • Choosing between integration approaches with different infrastructure requirements.

Direct execution fits tasks with one reasonable shape: a single-file fix where the stack trace names the line, or adding one validation conditional. Planning those produces a plan saying "add the null check". That is friction with no safety gain.

Timing (the point people get backwards): the complexity is stated in the request. "Restructure into microservices" announces it in the first sentence. The distractor is starting in direct execution "to see how far you get" and switching to plan mode once things get messy. By then you've made irreversible choices across many files. Choose plan mode at the outset.

The Explore subagent

Investigation can consume the context budget the rest of the task needs: mapping 45 call sites, surveying service boundaries, dead ends. The Explore subagent does the verbose discovery in its own isolated context and returns a summary. It is the same move as context: fork (Chapter 5 covers subagent mechanics). Use it in the investigation phase of a multi-phase task so exploration doesn't exhaust context before you act. A plan that had to read all 45 files in-session leaves no room to discuss it.

Chapter 11 — Claude Code in CI

Interactive Claude Code waits for you when it's stuck or needs permission. In a pipeline nobody answers, so the job hangs until the runner times out. This chapter (task statement 3.6) covers what makes Claude Code a CI participant: a flag that never waits for input, flags for machine-parseable output, and CLAUDE.md as the way to tell an unattended instance what "good" looks like.

Running example: a PR review bot that checks a diff against team standards and posts inline comments. Secondary example: test generation for changed code.

The flag that prevents the hang: -p

-p / --print: non-interactive, single-shot. It takes the prompt, does the work, writes to stdout, and exits. No follow-up questions, no blocking on stdin. This is sample question 10: "a CI job hangs waiting for interactive input — what fixes it?"

claude -p "Review the diff between origin/main and HEAD for correctness issues, \
security concerns, and violations of the standards in CLAUDE.md" \
  --output-format json \
  --json-schema "$(cat ./ci/review-schema.json)"

Reject by name:

  • CLAUDE_HEADLESS: doesn't exist.
  • --batch: doesn't exist.
  • < /dev/null: a generic Unix trick. It doesn't use Claude Code's non-interactive contract (write stdout, exit).

For GitHub Actions specifically, the official anthropics/claude-code-action wraps headless claude -p. It takes claude_args (e.g. --json-schema) and exposes structured_output as an Actions output. It is more idiomatic than hand-rolled subprocess calls, and the code below is what it does under the hood.

Structured findings: --output-format json and --json-schema

The consumer is a script that posts inline comments at file and line, or decides pass/fail. Parsing prose breaks as soon as a word changes.

  • --output-format json: output is JSON.
  • --json-schema: constrains that JSON to your schema (fields, types, required), so the bot can deserialise into a known type.

Use them together. An option naming --output-format json alone, or regex-parsing prose, is a distractor.

Two mechanical gotchas the CLI enforces (the guide doesn't mention them):

  1. --json-schema takes the schema inline as a JSON string, not a file path. --json-schema ./ci/review-schema.json fails with --json-schema is not valid JSON. Keep the file in git, but pass its contents: "$(cat ./ci/review-schema.json)".
  2. Response shape. --output-format json returns a single JSON object (result, session_id, usage, total_cost_usd, and structured_output when a schema is passed). Read json.loads(stdout)["structured_output"]. The array of events (system/assistant/user/result) belongs to --output-format stream-json, a newline-delimited stream for live progress (token-level needs --verbose --include-partial-messages). Treating the json output as an array gives a TypeError.

Non-interactive execution: --bare, permissions, and no one left to ask

  • --bare is recommended for CI and scripting. It skips auto-discovery of hooks, skills, commands, subagents, plugins, MCP servers, CLAUDE.md, and auto memory, for determinism across runners.   • Permission prompts stall a pipeline like unanswered stdin. Settle them up front:

CLAUDE.md as the CI context mechanism

A CI instance has no memory of your interactive sessions. It doesn't know "no magic numbers" or "use Fixtures.customer()". CLAUDE.md is the mechanism for supplying testing standards, fixture conventions, and review criteria, loaded the same as in interactive sessions (without --bare).

Write specifics, not platitudes. "Follow best practices" adds nothing. "Flag any process_refund call without an idempotency key" encodes what you've been burned by.

Test generation: documenting what a valuable test looks like

Asking for "tests for this" produces lots of low-value tests: restating the type checker, testing getters. The Code Generation scenario's fix: document testing standards, valuable-test criteria, and available fixtures in CLAUDE.md. For example:

  • One test per distinct business rule, not per code path.
  • Constructor and trivial-getter tests aren't valuable.
  • Use the Fixtures module, not inline literals.
  • Refund-window and partial-refund edge cases are always worth covering. Description-field formatting variants are not.

Why the session that wrote the code is a poor judge of it

Having the session that just wrote the code review it seems efficient. It works worse than an independent instance, and the exam asks why:

  • While writing, the session made many small calls (skip this unlikely edge case, this name is close enough, this shortcut is fine), each reasonable in context.
  • Reviewing its own work, it grades decisions it just rationalised. Its context carries momentum toward "this is fine", and self-consistency makes it stick with earlier judgements rather than reopen them.
  • A fresh claude -p reads the diff cold against CLAUDE.md with no investment in those choices, so it is better placed to catch the skipped null check or the misused fixture.

The CI pipeline should run a separate review step. "Have the generating session review it" is the trap. Chapter 15 develops the general principle.

Chapter 12 — Prompt engineering

Every CLAUDE.md line you tightened because Claude kept getting it wrong was prompt engineering. The exam doesn't ask for eloquent prompts. It asks you to diagnose the failure and pick the matching fix.

The key distinction (tasks 4.1 and 4.2): explicit criteria fix a rule that was never written down. Few-shot examples fix a rule that is written down but applied inconsistently. Both add words to a prompt aimed at the same symptom, and they treat different diseases.

Task 3.5 (iterative refinement) is separate. It covers the process you run with Claude Code to converge on a working prompt or implementation, not what the prompt contains.

The running example: a code review bot with a trust problem

A review bot (the Code Generation scenario) has run on every PR for a month. About one comment in three is noise: style nits labelled "medium", or false alarms on patterns standard in this codebase. Developers stop reading it, including the comment that would have caught a real bug.

False positives in one category erode trust in every category. The reader can't tell categories apart, so trust is one shared reservoir and one leaky category drains it.

The instinct is "be conservative" or "only report high-confidence findings". That is a named trap. General appeals to caution don't improve precision compared with specific categorical criteria. The model was already guessing at an undefined boundary. "Be conservative" makes it guess less often, in both directions, in a ratio you didn't choose.

4.1 — When the rule itself does not exist

Write the rule down.

  • Vague: "Check that comments are accurate." A fuzzy standard, judged differently on Monday and Friday.
  • Explicit: "Flag comments only when claimed behavior contradicts actual code behavior." An operational test: read the claim, read the code, check for contradiction.

The general skill is to state which categories to report and which to skip, not to filter by confidence. Confidence is the model's self-assessment of an undefined question, and it is no more reliable than the question. Put bugs and security in scope, minor style and locally idiomatic patterns out, stated as rules about the code.

Python

4.2 — When the rule exists but bends on hard cases

The criteria are in place and good. The bot gets the obvious cases right, but is inconsistent near the boundary. process_refund catches a broad exception and logs without re-raising: arguably a bug, arguably deliberate degradation. It's flagged on some runs and not others. The rule is defined and applied inconsistently where judgement is needed. Use few-shot examples.

Few-shot means 2–4 fully worked examples in the prompt: input, reasoning, output. It is the most effective technique for consistent, actionable output when prose keeps producing variation, because an example demonstrates the reasoning behind an ambiguous call, and the model can generalise that reasoning to novel cases. You aren't enumerating every pattern. You're showing how to weigh competing considerations.

Show the reasoning, not just the verdict.

  • "diff X → no finding" teaches one answer.
  • "diff X → broad catch swallows the exception without logging the customer-facing error path, no upstream handler visible, so a bug, not deliberate degradation → BUG, medium" teaches the test to run next time.

Examples without reasoning generalise worse, and this is the axis the exam probes.

3.5 — Iterative refinement as a developer discipline

How you converge with Claude Code, turn by turn. Four techniques:

  1. Concrete input/output examples when prose fails. "Normalise dates, handling the three legacy formats" gets read inconsistently. 2–3 exact input → output pairs pin it down. It's the same mechanism as few-shot, used to communicate a spec during development. Named case: data-migration edge cases. Instead of "handle nulls sensibly", give customer_id: null, order_total: 45.00 → route to the quarantine table, don't insert with a fabricated ID.
  2. Test-driven iteration. Write tests first (expected behaviour, edge cases, performance requirements), then iterate by feeding Claude Code the test failures. A failing test is a precise, falsifiable statement of the gap, and every red test replaces a round of "no, I meant…".
  3. The interview pattern. Have Claude Code ask you questions first, as a competent engineer would before coding. It is most valuable in unfamiliar domains, where it surfaces things you wouldn't think to specify: cache invalidation strategy for a caching layer, failure modes of a job queue you've never run. It's the clarifying question in plan mode, invoked deliberately and up front.
  4. Single message vs sequential: do the problems interact?
    • Independent (a typo here, an unrelated off-by-one there): fix sequentially. Bundling adds nothing and makes each fix harder to verify.
    • Interacting (a caching bug plus an invalidation-ordering bug that only makes sense given the first): one detailed message. Fixed separately, the first fix can invalidate your description of the second or make it worse. Example: a migration's null-handling fix depends on where the transaction boundary lands.

Context awareness: a newer lever for long-running prompts

On Sonnet 5, Sonnet 4.6, Sonnet 4.5, and Haiku 4.5, Claude automatically receives <budget:token_budget> and <system_warning>Token usage: X/Y remaining</system_warning> as a conversation runs. So "as you approach your budget, stop exploring and write up what you have" now works without you computing the number.

It does not replace Chapter 14's case-facts block or manifest. Budget awareness paces work against a shrinking window. Those patterns decide which exact numbers and conclusions must survive compaction. A model that wraps up gracefully at 90% can still lose a dollar amount to summarisation.

Models older than Opus 4.7 don't get this automatically. They need an explicit task budget via a beta flag, stated in the prompt.

What the exam tests

  • 4.1/4.2 as a diagnostic pair. The top trap is "be more conservative" or "raise the confidence threshold". Treat any general appeal to caution as wrong.
  • Missing boundary (4.1): write criteria, define severity with concrete examples, or temporarily disable a collapsing category.
  • Shaky on ambiguous cases (4.2): 2–4 few-shot examples showing reasoning, distinguishing acceptable from real issues, demonstrating output format.
  • Extraction under 4.2: varied document structure and null-field fabrication are few-shot problems once the schema is correct. Schema problems are Chapter 13.
  • 3.5: concrete I/O examples after prose has failed; test-first with failures as feedback; interview pattern for unfamiliar domains; single message vs sequential depends on interaction.

Chapter 13 — Structured output

When output goes to a program rather than a person, "write a careful prompt, ask for JSON, hope" isn't good enough. Running example: extract_invoice, which returns vendor, line items, taxes, and total for an accounts-payable pipeline.

It fails in two different ways, with different fixes:

  • Syntax: malformed JSON (dangling comma, unescaped quote in "Smith & Sons"). Fixed by schema and tool use.
  • Semantics: well-formed JSON that is wrong (line items sum to $412.50, total says $391.00). Fixed by validation.

Using a stricter schema for a semantic error, or validation for a syntax error, is a misdiagnosis. The second half of the chapter covers volume: the Message Batches API.

Tool use as the extraction mechanism

A tool_use block's input conforms to the tool's input_schema. For extraction, the "tool" does nothing. extract_invoice touches no database. It exists so its schema becomes the contract, and tool_use.input arrives as a parsed object.

This is the most reliable way to get schema-compliant output. Asking for JSON in prose means validating a string after the fact, and a dropped brace shows up at json.loads, far from the cause. With tool use there's no string to parse, so malformed JSON is structurally impossible, not just less likely.

Two more mechanisms: output_config.format and strict tool use

  • output_config.format with {"type": "json_schema", "schema": {...}} is dedicated structured output with no tools involved. Supported JSON Schema subset (both mechanisms):

  • No numeric bounds (minimum, maximum, multipleOf).
  • No string length bounds.
  • additionalProperties must be false.
  • No recursive schemas.
  • Only a limited regex dialect for pattern.

Nullable ["string", "null"] and enum-plus-detail (below) still work. Move range and length checks into your own code.

Grammar compilation cost: the first call with a schema pays compile latency. The grammar is cached for 24 h from last use. Changing the schema invalidates it, and also invalidates prompt caching. Keep the schema fixed and put per-request variation in the prompt text.

  • Forced: force extract_invoice first when enrich_vendor_record needs vendor_name, or flag_for_review needs conflict_detected. Then return to "auto".

Schema design decisions that matter more than they look

  • Required fields invite fabrication. Require invoice_number and a receipt that lacks one will sometimes get an invented value. Make it nullable (["string", "null"]). An honest null trips your validation, while a fabrication sails through.
  • Enum with an escape hatch. category ∈ "goods", "services", "subscription", "other", plus category_detail, required when "other". You get clean aggregation on common cases and honesty on the rest.
  • "unclear" for judgement enums (paid/unpaid/disputed), so genuine ambiguity has a legitimate answer instead of a forced wrong guess.
  • Format normalisation goes in the prompt, not the schema. A string field accepts 03/14/2026, 14 Mar 2026, and 2026-03-14 alike. "Return dates as ISO 8601; if ambiguous, infer the most likely reading" does what no pattern can.

Syntax versus semantics — the load-bearing distinction

Schema compliance tells you the output parses, not that it's correct. The $412.50 vs $391.00 invoice is fully schema-valid. Structure says nothing about arithmetic, provenance, or internal consistency.

The exam's worked example: have the model do the arithmetic as a checkable field.

  • stated_total: the number printed on the document.
  • calculated_total: "sum of line_total across line_items, plus tax_amount. Compute this yourself; do not copy stated_total."

The model has to add up the lines instead of transcribing a headline, and your code diffs the two. A difference of more than a cent goes to a human before AP.

conflict_detected: a boolean the model sets for internal inconsistency (totals that disagree, two dates for one event, a name spelled two ways). It turns "the model might notice" into "the pipeline will notice".

Failure Fixed by
Malformed / unparseable JSON Schema + tool use (eliminated structurally)

Valid JSON, wrong values (don't reconcile, wrong field, fabrication) Validation logic, not a stricter schema

Validation, retry, and feedback loops

The tested skill is knowing which failures retry can fix:

  • Retriable: the information is in the document and the first pass got it wrong (an omitted field, a dropped line item, a miscalculated total).
  • Not retriable: the information isn't in the source (e.g. a PO in a system you never provided). Attempt five has no more access than attempt one, and an unguarded loop burns requests forever. Route to a human, or to a step that fetches the missing document.

Classify the failure before retrying. When you retry, send the original document + the failed extraction + the specific validation error, so the model fixes a named mistake.

Designing for batch volume

Message Batches API (task 4.5):

  • 50% cheaper, flat, not volume-tiered.
  • Processed within up to 24 hours, with no SLA for anything faster. Design for the slow case.
  • Not for multi-turn tool calling (see below).
  • Every request carries a custom_id.

The deciding question is latency tolerance, not cost: is anyone blocked waiting?

  • Fits: overnight tech-debt report, weekly compliance audit, nightly test generation, nightly invoice reconciliation. The consumer checks a dashboard tomorrow.
  • Doesn't fit: a pre-merge check. A developer can't wait an unknown 20 minutes to 24 hours.

The SLA arithmetic

Commitment: a 30-hour SLA, batching on a fixed schedule.

  • Worst case = wait until the next submission + up to 24 h of processing.
  • 30 − 24 = 6 h of budget for the wait.
  • Every 6 h gives a 30 h worst case, exactly at the ceiling with no margin.
  • Every 4 h gives 28 h worst case, a 2 h buffer. That is the answer.

Default rule: subtract the window from the SLA, then choose an interval comfortably inside the remainder, not at the boundary.

A batch request does not support multi-turn tool calling. Each entry is one call. It can return tool_use, but nothing executes the tool and feeds the result back. This breaks designs quietly rather than throwing an error.

  • Fits: invoice extraction, because extract_invoice is never executed. The tool block is just the vehicle for structured output.
  • Doesn't fit: look up a vendor mid-extraction, decide whether to flag, then extract. That loop needs multi-turn execution. Run it synchronously, or split it into a batch-friendly first pass plus a later step.

Handling failures without resubmitting everything

  • Results come back errored, canceled, or expired for some fraction. Resubmit only the failed custom_ids, never the whole batch.
  • Fix, don't just retry: if failures share a cause (oversized scans exceeding context), chunk those documents before resending.
  • Refine on a sample first: run 50–100 invoices synchronously and iterate until first-pass success is high, then batch the full volume. Discovering a date-format gap after a day-long batch costs the day plus the redo.

Chapter 14 — Context engineering

Two hours into a session, answers soften ("typically follows the pattern used elsewhere") and after /compact a decision from 20 minutes ago has to be repeated. The cause is the same in both cases: the messages array is finite, everything the agent knows lives in it, and neither growth nor compression is free.

This chapter covers two problems that look alike. Mixing up their fixes is the mistake to avoid.

5.1 — Preserving facts inside one long conversation

Three failures compound:

  1. Progressive summarisation destroys specifics. Paraphrase keeps the gist and loses numbers. "Customer disputed a charge and we discussed a refund" is a faithful summary of "disputed a $284.17 charge on SO-88213, promised a refund by the 15th, second contact". The amount, order ID, and date are gone. That is what summarisation does, not a bug.
  2. Lost in the middle. Models attend reliably to the start and end of long input and worse to the middle. A fact stated once mid-conversation is at higher risk of being ignored. This is structural, not something an upgrade patches.
  3. Tool results cost tokens by size, not relevance. A realistic lookup_order returns 40+ fields (SKUs, routing codes, tax flags, three address blocks). A return needs five: order id, item, amount, ship date, status. Nothing removes an appended result, so three lookups bury the signal under a hundred-plus irrelevant fields, reprocessed every turn.

Constraint: the API is stateless, so you must pass the complete history every request. Dropping earlier turns to save tokens doesn't leave the model with a rough understanding. It structurally cannot know what it doesn't have.

On Claude 4.5+, running out of room mid-generation gives stop_reason: "model_context_window_exceeded" (older models reject the request outright). Handle it separately from max_tokens. The effect looks similar, but the cause is different.

The case-facts block

The fix is architectural: extract transactional facts (amounts, dates, order numbers, statuses, customer-stated expectations) into a structured block that you include in full in every prompt, outside summarised history. It is the per-conversation equivalent of CLAUDE.md sitting in system rather than messages.

Python

from dataclasses import dataclass, field
from typing import Optional

@dataclass
class CaseFacts:
    """Durable, non-summarizable facts for one support case."""
    customer_id: Optional[str] = None
    tier: Optional[str] = None
    issues: list[dict] = field(default_factory=list)
    # each issue: {order_id, amount_cents, status, promised_date, stated_by_customer}

    def render(self) -> str:
        lines = [f"CASE FACTS (verified, do not paraphrase):",
                  f"customer_id={self.customer_id} tier={self.tier}"]
        for i, issue in enumerate(self.issues, start=1):
            lines.append(
                f"  issue {i}: order={issue['order_id']} "
                f"amount=${issue['amount_cents']/100:.2f} "
                f"status={issue['status']} "
                f"promised_by={issue.get('promised_date', 'n/a')}"
            )
        return "\n".join(lines)

    }

  • Rebuilt each request from your application state, not produced by asking the model to summarise itself. The point is that it never passes through lossy compression.
  • A separate layer per issue in multi-issue sessions. A billing dispute plus a later shipping complaint each keep their own order id, amount, and status. In one paragraph, the second issue's amount can quietly borrow the first's. Structured issue data lets the agent answer "status of the shipping issue?" without wading through the billing discussion.

Trimming tool output at the source

The case-facts block protects facts after extraction. Tool bloat happens earlier, when lookup_order returns. Trim before appending. The tool boundary is a design decision: the function the agent calls projects the full record down to what the task needs.

Chapter 15 — Escalation, review, and provenance

Three problems at the point where a system produces an answer: who checks it (4.6), when the system should refuse to answer alone (5.2), and how humans review at scale and how evidence survives synthesis (5.5, 5.6). They share a temptation: let the model check itself, decide for itself when it's out of its depth, or let a summary drop the citations. They also share a villain: the model's opinion of itself. The last section resolves an apparent contradiction about confidence scores. If you remember one thing from this chapter, make it that.

Review architecture: why a second instance beats a second look

"Review the diff you just wrote" sometimes catches a typo but rarely questions a decision. The reason is structural. A model reviewing its own output in the same session keeps the reasoning context from generation. It isn't reading the code fresh. It is re-reading its own justification and stays biased toward it.

Extended thinking doesn't fix this. More reasoning helps generation, but the bias isn't too little effort. The reasoning already happened and now anchors the read. A human is likewise a worse reviewer of their own PR than a colleague who didn't watch it get written.

Fix: an independent instance whose context holds only the artifact (diff, extraction, plan) and none of the generator's reasoning. It catches subtle issues that both self-review instructions and extended thinking miss.

Escalation and ambiguity resolution: what actually earns a handoff

Escalating too often is expensive and useless. Escalating too rarely is dangerous. The exam's answer is a closed list of three valid triggers:

  1. The customer explicitly asks for a human.
  2. Policy has a gap the agent lacks authority to resolve.
  3. The agent can't make meaningful progress after a real attempt.

Anything else ("felt hard", "seemed upset", "wasn't sure") misfires both ways: it escalates easy cases that looked complex, and grinds on hard cases where the model was confidently wrong.

Trigger 1 details:

  • Explicit request: escalate immediately. No "let me just check one thing first". Investigating anyway treats the stated preference as an obstacle.
  • Frustrated but no request: not a trigger. Acknowledge the frustration, offer to resolve if it's within capability, and escalate only if they reiterate. What counts is what they asked for, not what tone implied.

Trigger 2, policy gap. The policy covers price drops on your own site and says nothing about competitor price matching. "Policy doesn't forbid it" invents unapproved policy. "Not covered, so no" denies something the business might want. Both are wrong because the agent lacks authority either way. The silence is the trigger.

Trigger 3, no progress. It is measured by outcome (tools and reasonable alternatives tried and exhausted), not by a forecast before trying.

Two named invalid proxies:

  • Sentiment. It doesn't correlate with complexity. An angry customer can have a trivial issue, and a calm one a case the agent shouldn't handle alone.
  • Self-reported confidence. A model wrong about a hard case is often wrong about being wrong. The limitations that made the case hard also corrupt its self-assessment, so it says "confident" on exactly the cases it's likely to get wrong.

Fix: explicit escalation criteria in the system prompt, plus few-shot examples in both directions: a case that looks complex but resolves cleanly, and one that looks simple but hits a policy gap.

Human review workflows and confidence calibration

The aggregate-accuracy trap. "97% accurate" invites cutting human review. But 97% overall is consistent with 99.5% on the dominant invoice type and 60% on a rare type or a hard field (foreign-currency total, handwritten date, vendor-specific field). Automate on the aggregate and you remove oversight exactly where it's needed. Validate accuracy by document type and by field, and confirm it holds in every segment before reducing review on any.

Two ongoing mechanisms (not one-off checks):

  • Stratified random sampling of high-confidence extractions, the ones that would otherwise go unseen. That's how you measure the true error rate on the bucket you aren't otherwise checking, and catch new error patterns early.
  • Field-level confidence, calibrated on a labelled validation set. Per-field scores are checked against ground truth, and 0.9 should mean right about 90% of the time, not 65%. Once calibrated, route low-confidence fields and documents with contradictory sources to humans first, so limited reviewer time goes where errors are most likely.

Python

Provenance in multi-source synthesis

Subagents gather from different sources and synthesis combines them. The failure is quiet: a right answer that can't say where it came from.

Why attribution gets lost: summarisation's job is to compress, and a citation looks like detail safe to drop, since the claim survives without it. After two or three passes, the report is full of confident, unattributed claims indistinguishable from verified ones.

Fix (structural): every subagent outputs claim-source mappings (claim + source URL or document name + supporting excerpt), and every downstream step, including synthesis, preserves and merges them. "Summarize these findings" invites loss. "Merge these findings; every claim must carry the source mapping it arrived with" makes a dropped citation a visible, checkable defect.

The confidence contradiction, resolved

The chapter appears to contradict itself:

  • Self-reported confidence is not a valid escalation trigger (5.2).
  • Yet field-level confidence drives review routing (5.5), and review passes self-reporting confidence is good design (4.6).

The resolution is calibration.

  • Uncalibrated self-report is the model's guess about itself, made by the system whose competence is in question. The case where it's most likely silently wrong is also where its self-assessment is most likely wrong, for the same reason. Two unreliable signals don't make a reliable one.
  • Calibrated score: computed the same way, but checked against a labelled validation set and shown to track the true error rate (0.9 ≈ 90% correct on ground truth). It has stopped being an opinion and become a measurement, like any instrument verified before use.

Rule: never let a raw, unchecked self-report make an autonomous decision (to escalate, or that code is correct). Once calibrated against ground truth, a score is a legitimate routing input for human review.
